## Funciones

- **Recuento exacto de tokens**: desglose de tokens de entrada/salida/caché
- **Integración con statusline** *[nuevo]*: añade un indicador de uso de tokens en vivo a la statusline de Claude Code (o cualquier agente que pueda acceder a un endpoint HTTP local) — ver [Integración con statusline](#integración-con-statusline)
- **Calendario de contribuciones**: heatmap 2D + vista isométrica 3D con métricas de Tokens/Cost/Messages
- **Explorador de sesiones**: análisis detallado por sesión
- **Pestaña Quota** *[nuevo]*: barras de ventana de suscripción con cuenta atrás de reinicio para Codex, Claude Code y Antigravity. Las ventanas de Codex funcionan desde los logs locales; los créditos de reinicio de Codex, las funciones con medidor y todas las cuotas de Claude/Antigravity necesitan [consulta en vivo](#seguimiento-de-cuota-opcional) con opt-in
- **App de barra de estado Companion** *[nuevo]*: consulta el gasto y la cuota de suscripción desde la barra de menú de macOS o el área de notificaciones de Windows — para Windows en [Microsoft Store](https://apps.microsoft.com/detail/9ppnmpdq8b52) — [capturas y descargas](#tokdash-companion-app-de-barra-de-estado)
- **Vistas multiseservidor**: añade servidores de Tokdash de WSL, macOS u otros en Ajustes; combina el uso de cualquier selección manteniendo la cuota agrupada por máquina. Ver [acceso remoto](docs/guides/REMOTE_ACCESS.md).
- **Temas y acabado de la app**: 17 temas de estilo, modo claro/oscuro, soporte de instalación PWA y UI en 6 idiomas (English / 中文 / 日本語 / 한국어 / Español / Português)

### Configuración

1. Instala y arranca **Tokdash 1.5.2 o superior** usando el [Inicio rápido](#inicio-rápido).
2. Instala el companion. En Windows, usa el enlace de Microsoft Store de arriba. Para descarga directa, obtén el asset de tu plataforma y verifícalo contra `SHA256SUMS`.
3. Desde una descarga directa: en macOS, abre el DMG y arrastra `TokdashCompanion` a Aplicaciones; en Windows, descomprime el ZIP en un directorio estable y ejecuta `TokdashCompanion.exe`.
4. El companion se conecta por defecto a `http://127.0.0.1:55423`. Abre su configuración para añadir, probar, nombrar, activar o quitar endpoints de Tokdash explícitos, incluidas URL privadas de Tailscale Serve.

El companion solo contacta con los endpoints de Tokdash que configures. Las notificaciones de cuota baja y el arranque al iniciar sesión son opt-in y desactivados por defecto. Consulta la [guía de publicación del companion](companion/docs/RELEASE.md) para instrucciones de checksums, actualizaciones y eliminación.

## Inicio rápido

### Soporte por plataforma

- **Linux (incluido WSL2):** soportado
- **macOS:** soportado
- **Windows (nativo):** experimental

### Requisitos previos

- Python **3.10 o superior**
- Uno o varios [clientes compatibles](docs/reference/SUPPORTED_CLIENTS.md) instalados

### Instalación

Instalación aislada recomendada:

```bash
pipx install tokdash
```

Si no usas pipx:

```bash
python3 -m pip install --user tokdash
```

### Primer arranque

Ejecuta el asistente de iniciación:

```bash
tokdash setup
```

El asistente configura un servicio de fondo a nivel de usuario reversible cuando la plataforma lo permite, e imprime la URL del panel (por defecto: `http://127.0.0.1:55423`). Si no hay ningún gestor de servicios soportado, registra el estado de la configuración e imprime indicaciones para ejecutar en primer plano. Usa valores por defecto que priorizan localhost, no requiere `sudo` para el servicio local y conserva tu historial de uso salvo que más adelante desinstales con `--purge`.

Para exponer el panel explícitamente en todas las interfaces de red con escritura desactivada, ejecuta `tokdash setup --bind 0.0.0.0`; revisa primero la [guía de acceso remoto](docs/guides/REMOTE_ACCESS.md).

Para una configuración no interactiva desde un agente, script o paquete:

```bash
tokdash setup --auto --json
```

Para previsualizar qué cambiaría la configuración:

```bash
tokdash setup --dry-run
```

### Verificar

```bash
tokdash doctor
```

`doctor` comprueba el runtime, el servicio de fondo, el puerto configurado, las rutas de datos y el estado de la comprobación de actualizaciones. Usa `tokdash doctor --json` para automatización.

### Actualizar o eliminar

```bash
tokdash update       # actualiza el runtime gestionado y reinicia el servicio cuando es posible
tokdash uninstall    # revierte exactamente lo que creó setup; conserva el historial de uso por defecto
```

`update` solo maneja métodos de instalación que Tokdash puede gestionar con seguridad. Si tu runtime fue instalado por un gestor de paquetes que Tokdash no controla, imprime las instrucciones manuales exactas en lugar de modificar ese entorno. Para runtimes gestionados, `update` informa de la versión de Tokdash antes y después de la actualización; si la versión no cambia, indica que Tokdash ya está en esa versión en lugar de sugerir que se instaló un paquete nuevo.

<details>
<summary>Instalaciones existentes: migración desde antes de v1.0</summary>

Si instalaste Tokdash antes del flujo de iniciación, actualiza primero:

```bash
pipx upgrade tokdash
# o: python3 -m pip install --user -U tokdash
```

Luego ejecuta `tokdash doctor` y `tokdash setup` cuando quieras que Tokdash gestione el servicio de fondo. Si ya tienes un servicio systemd o launchd escrito a mano, setup **no** lo sustituye en silencio: por defecto rechaza archivos `tokdash.service` / plist sin marca. Sigue gestionando ese servicio tú mismo, elimínalo antes de configurar, o ejecuta `tokdash setup --force` después de revisar `tokdash setup --dry-run`. `--force` también trata con servicios anteriores a 1.0 que ya ocupan el puerto `55423` pero no exponen la nueva huella `/health`: reescribe y reinicia el `tokdash.service` existente. Usa `tokdash setup --no-service` para omitir la creación del servicio.

Si tu configuración actual usa un interpretador de conda/sistema/pip de usuario y quieres que `tokdash update` gestione las actualizaciones futuras, migra el servicio al venv propiedad de setup de Tokdash:

```bash
# Actualiza el comando tokdash que vas a ejecutar, por ejemplo:
python3 -m pip install --user -U tokdash
# o, para una instalación en conda base:
conda run -n base python -m pip install -U tokdash
tokdash setup --runtime venv --force
tokdash doctor
```

Esto conserva tu historial de uso en `~/.tokdash`, reescribe el servicio de usuario para ejecutar `~/.tokdash/runtime/python-venv/bin/python -m tokdash` y permite que futuros `tokdash update` actualicen ese venv gestionado y reinicien el servicio. Si instalaste con pipx, puedes mantener el runtime de pipx y actualizar con `tokdash update` o `pipx upgrade tokdash`.

</details>

### Acceso remoto

Tokdash sigue vinculado a loopback por defecto. `tokdash setup` interactivo puede configurar Tailscale Serve tras una confirmación explícita, proporcionando acceso de lectura HTTPS privado desde Windows u otro dispositivo del tailnet. Usa reenvío SSH cuando necesites acceso de escritura autenticado. Un `--bind 0.0.0.0` explícito proporciona acceso de red de solo lectura pero expone el panel sin autenticar en cada interfaz alcanzable.

Consulta **[`docs/guides/REMOTE_ACCESS.md`](docs/guides/REMOTE_ACCESS.md)** para comandos de configuración, indicaciones de WSL2, URLs de acceso, comportamiento de escritura y compromisos de seguridad.

### Alternativa en primer plano

Si solo quieres un proceso de primer plano puntual:

```bash
tokdash serve
```

Abre `http://127.0.0.1:55423`. Usa `tokdash serve --port <puerto>` si el puerto por defecto está ocupado.

Para todos los detalles de la iniciación, incluidas opciones de runtime, comportamiento de WSL/systemd, launchd de macOS, Tailscale, empaquetado y actualizaciones, consulta la ayuda de `tokdash setup` y la documentación.

### Digest de OpenClaw (informes programados)

## Configuración

Tokdash es **solo localhost por defecto**.

- `TOKDASH_HOST` (por defecto: `127.0.0.1`)
- `TOKDASH_PORT` (por defecto: `55423`)
- `TOKDASH_CACHE_TTL` (por defecto: `600` segundos)
- `TOKDASH_CACHE_MAX_ENTRIES` (por defecto: `256`) — limita respuestas de API en caché y sus bloqueos de inactividad por clave
- `TOKDASH_COMPUTE_CONCURRENCY` (por defecto: `2`) — tope de reparseos pesados de historial simultáneos; las peticiones frías excedentes devuelven un `503` rápido en lugar de saturar el servidor bajo carga
- `TOKDASH_STARTUP_WARM_JOIN_SECONDS` (por defecto: `30` segundos) — cuánto espera la primera petición de una clave que aún se está calentando en el arranque en lugar de devolver `503`; como máximo una petición por clave espera
- `TOKDASH_LIMIT_CONCURRENCY` (por defecto: `64`) — tope de conexiones de uvicorn (backpressure)
- `TOKDASH_KEEPALIVE` (por defecto: `5` segundos) — timeout keep-alive de uvicorn
- `TOKDASH_ALLOW_ORIGINS` (separado por comas, por defecto: vacío)
- `TOKDASH_ALLOW_ORIGIN_REGEX` (la política CORS por defecto permite localhost/127.0.0.1 y lecturas de Tailscale Serve del mismo tailnet; fijar cualquiera de las opciones CORS sustituye esa política por defecto)
- `TOKDASH_NO_RETENTION_NOTICE` (fijar en `1` para silenciar el recordatorio de retención del historial que imprime `tokdash serve`)
- `TOKDASH_SETUP_NO_OPEN` (fijar en `1` para omitir la apertura opcional del navegador al final de `tokdash setup`)

Tiempo activo de sesión (estimado):

Cada sesión informa `active_ms` junto a `span_ms`. Span va del primer al último evento; el tiempo activo resta la inactividad contando cada hueco entre eventos de tokens consecutivos solo hasta un tope de inactividad, de modo que una sesión dejada abierta toda la noche ya no se lee como una sesión de 14 horas.

Es una estimación y la API lo dice: `summary.active_time_estimated` es `true` y `summary.active_time_method` es `capped-inter-event-gap`. Los límites vienen del método — una pausa corta entre eventos es indistinguible del trabajo, una operación única más larga que el tope se trunca a él, y una sesión con un solo evento de tokens mide cero porque nada la precede.

El trabajo concurrente se cuenta de dos formas. `active_ms` es tiempo de reloj, con la solapamiento contada una vez; `active_ms_sum` suma la solapamiento, es decir, tiempo de agente. Ambos aparecen por sesión y por herramienta en `summary`. Los agentes de Kimi y los subagentes de Claude corren junto al agente principal, y cada uno se mide como su propio flujo: un subagente que trabaja un minuto en paralelo añade un minuto de tiempo de agente y ninguno de tiempo de reloj.

- `TOKDASH_ACTIVE_GAP_CAP_SECONDS` (por defecto: `300`) — tope de inactividad en segundos; los huecos más largos solo aportan el tope. Acotado a 1s–6h.

BD de uso persistente (activa por defecto):

Tokdash mantiene por defecto un índice SQLite local en `~/.tokdash/usage.sqlite3`. Almacena filas de tokens analizadas y resúmenes de sesiones de Codex/Claude/Kimi/DeepSeek Harness/Reasonix para que las lecturas repetidas del panel y la API usen SQL indexado en lugar de reparsear cada log de origen. Los logs de origen siguen siendo la fuente de verdad; la BD es un índice de rendimiento local, y Tokdash vuelve al parsing en vivo si se desactiva o no está disponible.

Las filas de sesión en caché son neutrales en precio: conservan los inputs de facturación de cada turno (modelo, entrada fresca, lecturas y escrituras de caché, salida), y el coste se calcula al leerlas con la tarifa que ese proceso tenga cargada. Editar una tarifa reprecia al instante en lugar de releer gigabytes de logs, y dos versiones de Tokdash que comparten una base de datos no invalidan las filas de la otra por precio. Compartir solo es seguro mientras ambas builds soporten el mismo esquema de base de datos: las migraciones de esquema van solo hacia adelante, así que una vez que la build más nueva migra el archivo, la antigua se niega a abrirlo hasta que se actualice, y todas las lecturas en caché fallan hasta que las versiones coinciden. `tokdash doctor` informa del esquema en disco junto al que soporta la build en ejecución. Los cambios de parser y de archivos de origen se reparsean con normalidad. Las filas escritas antes de esto (incluidas las conservadas por `TOKDASH_USAGE_DB_DURABLE` tras desaparecer su log) se reprecian desde sus totales almacenados, lo que reproduce el mismo cifra pero no puede separar una escritura de caché de Claude o Kimi de la entrada fresca; solo un reparseo de esos logs puede restaurar esa distinción. Codex factura como `provider/model` y almacena el nombre plano, así que sus filas antiguas se reparsean una vez en lugar de reutilizarse.

Ejecuta un checkout contra su propio directorio de datos para que nunca migre la base de datos del servicio instalado:

```bash
TOKDASH_DATA_DIR=output/dev-data PYTHONPATH=src python3 main.py
```

- `TOKDASH_USAGE_DB` (por defecto: `1`) — fija `0`, `false`, `no` u `off` para desactivar la BD de uso persistente
- `TOKDASH_DATA_DIR` (por defecto: `~/.tokdash`) — directorio base del estado local de Tokdash
- `TOKDASH_USAGE_DB_PATH` (por defecto: `$TOKDASH_DATA_DIR/usage.sqlite3`) — ruta explícita del archivo SQLite
- `TOKDASH_USAGE_DB_DURABLE` (por defecto: `1`) — conserva filas ya indexadas si un archivo de origen desaparece temporalmente o un parser no devuelve filas; fija `0` para sustitución estricta de origen
- `TOKDASH_USAGE_DB_WATCH` (por defecto: `0`) — fija `1` para ejecutar un bucle de sincronización en fondo dentro de `tokdash serve`
- `TOKDASH_USAGE_DB_WATCH_INTERVAL` (por defecto: `30` segundos) — intervalo de sincronización de `tokdash db watch` y del bucle de observación durante serve

Comandos de mantenimiento de la BD:

```bash
tokdash db status --pretty
tokdash db sync --pretty
tokdash db verify --verify-period today --pretty
tokdash db repair --dry-run --pretty
tokdash db resync --pretty
tokdash db watch --pretty
```

Para acceso remoto a través de Tailscale Serve, reenvío SSH o vinculación de red explícita, consulta
[`docs/guides/REMOTE_ACCESS.md`](docs/guides/REMOTE_ACCESS.md). El `tokdash setup` interactivo puede configurar y
registrar la regla de Tailscale Serve tras tu opt-in.

Por defecto `tokdash serve` abre el panel en tu navegador una vez al arrancar. Pasa `--no-open` para desactivarlo (también se omite automáticamente en entornos headless/SSH y en las plantillas de servicio de fondo).

## Privacidad y seguridad

- **Sin telemetría**: Tokdash no envía tus datos a ningún sitio intencionadamente.
- **Parsing local**: el uso se calcula a partir de archivos de sesión locales (ver [clientes compatibles](docs/reference/SUPPORTED_CLIENTS.md)).
- **Consulta de cuota opcional**: la pestaña Quota es solo local por defecto. La consulta de API por proveedor se puede activar desde la pestaña o con `tokdash quota consent`; usa tus credenciales locales de CLI solo para llamar al endpoint de cuota de ese proveedor, y almacena las respuestas en la BD SQLite local de uso.
- **Exposición del servidor**: Tokdash se vincula a `127.0.0.1` por defecto. Tailscale Serve proporciona acceso privado de solo lectura, el reenvío SSH proporciona acceso de escritura autenticado, y `--bind 0.0.0.0` expone explícitamente lecturas sin autenticar en todas las interfaces. Ver la [guía de acceso remoto](docs/guides/REMOTE_ACCESS.md).

### Seguimiento de cuota (opcional)

La pestaña Quota muestra ventanas de utilización de suscripción y temporizadores de reinicio, a partir de dos fuentes de datos. **Logs locales** (sin red): Codex registra su propia cuota en archivos de sesión, así que las ventanas de 5 horas/semana de Codex funcionan desde el primer momento — pero solo se actualizan cuando usas Codex, y los logs nunca contienen créditos de reinicio ni ventanas de funciones con medidor. Trata el consumo de Codex desde logs de sesión como una **estimación que puede estar muy errada**: cada sesión cachea su instantánea de cuota en su última consulta y la reproduce sin cambios en cada mensaje posterior, de modo que las cifras pueden estar desactualizadas, y el ruido en los límites de reinicio puede distorsionar aún más una ventana — la pestaña Quota etiqueta estos gráficos como estimados. **Consulta en vivo** (desactivada por defecto, consentimiento por proveedor): Tokdash llama al endpoint de cuota del propio proveedor con la sesión iniciada que ya tiene tu CLI. Es más fresca, añade créditos de reinicio de Codex y funciones con medidor, es necesaria para el consumo de Codex **exacto**, y es la única fuente de cuota para Claude Code, Antigravity, MiniMax, Kimi Code y SuperGrok/Grok Build:

La cuota de Z.ai Coding Plan también está disponible únicamente mediante la consulta en vivo.

```bash
tokdash quota consent --codex-api on --claude-api on --antigravity-api on
tokdash quota consent --minimax-api on --kimi-api on --grok-api on --zai-api on
tokdash quota consent --credential-scan on   # permite los lectores locales de credenciales divulgados
tokdash quota consent --poll-interval 30      # cadencia de consulta en fondo: 15, 30, 60 o 120 min
tokdash quota consent --enabled off           # interruptor general: apaga TODO el seguimiento de cuota
tokdash quota poll
tokdash quota show
```

**Interruptor general.** `quota.enabled` (activado por defecto) enciende o apaga *todo* el trabajo de cuota — escaneo de sesiones, consulta de red y escritura de instantáneas. Actívalo desde la pestaña Quota o con `tokdash quota consent --enabled on|off`. Cuando está apagado (o se fija el interruptor de emergencia `TOKDASH_QUOTA_POLL=0`), el consultor de fondo queda completamente inactivo, `GET /api/quota/refresh` devuelve un error "quota tracking disabled" y la pestaña muestra una tarjeta de *activar seguimiento de cuota* en lugar de datos. Las claves de consentimiento por proveedor conservan su significado más estrecho, solo de red.

**Intervalo de consulta.** El consultor de fondo toma instantáneas cada **30 minutos** por defecto. Elige 15/30/60/120 minutos desde la pestaña Quota, durante `tokdash setup`, o con `tokdash quota consent --poll-interval N`; se guarda como `quota.poll_interval_minutes` en `config.json`. La variable de entorno `TOKDASH_QUOTA_POLL_INTERVAL` (segundos, mínimo 300) sustituye el valor guardado, y la pestaña muestra qué fuente está activa. Los cambios de intervalo se aplican en el siguiente ciclo de consulta sin reiniciar el servidor. La ingestión de sesiones de Codex es incremental: tras un relleno inicial único de tu historial, cada ciclo solo lee por la cola los archivos de sesión que crecieron, de modo que una consulta en estado estable cuesta miliseguros de un solo dígito.

Para ventanas de cuota con reinicio fijo, el consultor también muestrea cerca del límite de reinicio para que el historial capture el máximo previo al reinicio y la línea de base posterior. El muestreo de límites está activado por defecto, solo llama al proveedor cuya ventana lo disparó, agrupa límites cercanos de proveedores y mantiene al menos 300 segundos entre ciclos de consulta del demonio. Fija `TOKDASH_QUOTA_BOUNDARY_POLL=0` para desactivarlo, `TOKDASH_QUOTA_BOUNDARY_POST=0` para desactivar solo las muestras posteriores al reinicio, o ajusta los adelantos de 120 segundos por defecto con `TOKDASH_QUOTA_BOUNDARY_PRE_SECONDS` y `TOKDASH_QUOTA_BOUNDARY_POST_SECONDS`.

La consulta en vivo requiere dos decisiones separadas: `quota.credential_scan` permite el acceso de solo lectura a los almacenes de credenciales locales divulgados, y luego cada clave `<provider>_api` permite la petición de red de ese proveedor. Tokdash lee archivos de autenticación/configuración de CLIs nativos, `auth.json` de OpenCode más la configuración global de proveedores, los ajustes activos de Claude y la tabla `providers` de CC Switch a través de una conexión SQLite de solo lectura. Nunca explora logs de proveedores, perfiles de shell ni referencias arbitrarias de `{file:...}`. MiniMax acepta un inicio de sesión `mmx` o una Token Plan Subscription Key (`MINIMAX_TOKEN_PLAN_GLOBAL_KEY` / `MINIMAX_TOKEN_PLAN_CN_KEY`); una clave normal de pago por uso no está garantizada de tener cuota de Token Plan. Kimi acepta un inicio de sesión/clave de Kimi Code (`KIMI_API_KEY`), no una clave de pago por uso de Moonshot Open Platform. La cuota de SuperGrok/Grok Build requiere el inicio de sesión OAuth de xAI en `$GROK_HOME/auth.json`; una clave de API de xAI normal no puede acceder a la facturación de consumo. En macOS, Claude Code puede requerir un permiso de solo lectura de Keychain de una sola vez. Tokdash nunca actualiza ni escribe credenciales de proveedor. `TOKDASH_QUOTA_POLL=0` es un interruptor de emergencia duro para todo el seguimiento de cuota. `tokdash export` excluye datos de cuota por defecto; usa `--include-quota` solo cuando quieras incluirlos intencionadamente en el JSON.

Z.ai acepta una clave de Coding Plan desde `$ZCODE_HOME/v2/config.json`, una configuración de herramienta compatible, `ZAI_API_KEY` o `Z_AI_API_KEY`, y consulta las ventanas de créditos de 5 horas/semanales además de los límites MCP heredados.

El uso de tokens de Grok Build también se analiza localmente desde `$GROK_HOME/logs/unified.jsonl`. Sus registros de inferencia exponen tokens de prompt, prompt en caché, completion y razonamiento; Tokdash los atribuye usando los eventos de modelo del mismo proceso CLI y calcula el coste desde la base de datos de precios normal. Los registros sin evento de modelo se omiten en lugar de asignarles un precio conjetural.

El uso y las sesiones de DeepSeek Harness (`dsh`) se leen localmente desde `$DSH_HOME/sessions/*/*/session.jsonl.zstd` (o `session.jsonl` sin comprimir), con `DSH_HOME` por defecto en `~/.dsh`. Cada log es una secuencia de marcos zstd concatenados; Tokdash decodifica todos los marcos, pliega el chunk inicial de uso de cada paso en su mensaje finalizado en lugar de contarlo dos veces, y omite el prefijo heredado de las sesiones derivadas para que padre e hijo nunca facturen dos veces los mismos tokens.

El uso y las sesiones de Reasonix se leen localmente desde `$REASONIX_HOME` (por defecto `~/.reasonix`): tokens por petición desde los logs diarios `stats/YYYY-MM-DD.jsonl`, y estructura de sesión desde `projects/*/sessions/*.jsonl`. Reasonix habla con los proveedores que nombre su `config.toml`, de modo que el par `provider/model` de cada fila se atribuye y precia a través de la base de datos de precios normal; los modelos autoalojados sin tarifa publicada cuentan tokens a coste cero. Reasonix registra el uso por petición y nunca marca un id de sesión, así que las filas del Explorador de sesiones muestran turnos, proyecto y momento sin recuentos de tokens — Resumen y Estadísticas llevan los totales completos.
El uso de ZCode se lee localmente desde `$ZCODE_HOME/cli/db/db.sqlite` (por defecto `~/.zcode/cli/db/db.sqlite`; `ZCODE_HOME` sigue el propio ajuste de ZCode). Cada fila `model_usage` es una petición de modelo, reintentos incluidos, y el `model_id` de la fila se precia a través de la base de datos de precios normal mientras `provider_id` (p. ej. `builtin:zai-start-plan`) se conserva como etiqueta. `input_tokens` de ZCode cuenta tokens de prompt en caché y sin caché juntos, así que la parte en caché se separa en su propio cubo y se factura a la tarifa de caché, y los tokens de razonamiento se muestran disuntos de la salida pero se facturan a la tarifa de salida. ZCode también aparece en la pestaña Sesiones: los turnos se leen de la misma base de datos, facturados por (turno, modelo) con las mismas reglas, solo sesiones de nivel superior, y un turno que no produjo tokens factibles aún acredita su tiempo medido al tiempo activo de la herramienta. La cuota Coding Plan de ZCode es datos de cuenta remota y queda fuera del alcance del parser local.

La cuota de Coding Plan está disponible mediante el consultor en vivo de Z.ai con consentimiento independiente.

El uso de WorkBuddy se lee localmente desde transcripciones `~/.workbuddy-ai/projects/*/*.jsonl` (`WORKBUDDY_DATA_DIR` toma una lista separada por comas de raíces para apuntar a otros almacenes, p. ej. un directorio de datos de Windows desde WSL). Cada fila de mensaje de asistente es una llamada de modelo; la parte en caché dentro de `prompt_tokens` se separa en su propio cubo y se factura a la tarifa de caché, y los tokens de razonamiento se muestran disuntos de la salida pero se facturan a la tarifa de salida. El id de modelo se conserva tal cual: los ids explícitos (p. ej. gpt-5.5) se precian a través de la base de datos de precios normal, mientras el alias del router Auto (`default-model`) no existe en la BD de precios y cuesta 0.00. El valor `credit` por turno se almacena solo como metadatos y no afecta al coste. La pestaña Sesiones lee las mismas filas de transcripción (una fila de asistente facturada = un turno) desde las mismas raíces.

El uso de Qoder se lee localmente de dos sitios: la base de datos SQLite de la IDE (`SharedClientCache/cache/db/local.db` bajo el directorio de datos de la IDE; la build QoderCN se prefiere a la internacional en Windows y WSL) y los logs JSONL de la CLI (`~/.qoder` y `~/.qoder-cn`, más `QODER_CONFIG_DIR` y `QODER_CLI_HOME` separados por comas). Del lado de la IDE, cuentan todas las filas `chat_message`, todos los roles: la parte en caché se separa de los tokens de prompt en su propio cubo y el modelo viene de `model_key` (`auto` cuando falta el nombre del router). Del lado de la CLI, el registro de facturación de la transcripción de cada petición se combina con su registro de tokens de segmento en todas las raíces: las filas con créditos de proveedor conservan el coste informado por el proveedor como autoritativo, convertido a un estimado de $0.01 por crédito (`QODER_USD_PER_CREDIT` sustituye la estimación) y nunca se reprecia, mientras las filas solo con tokens se precian a través de la base de datos de precios normal. Un registro sin tokens de entrada los recupera de `context_usage_ratio` contra la ventana de contexto conocida — `auto` en 180.000 por defecto, cada modelo una vez fijada `QODER_CLI_CONTEXT_WINDOW` explícitamente. Qoder IDE aparece en la pestaña Sesiones: las mismas filas `chat_message` (todos los roles, una fila analizable = un turno) se leen desde una instantánea en directorio temporal de la misma base de datos.

El uso de Zed se lee localmente desde `threads/threads.db`, bajo el directorio de datos de Zed propio de cada sistema (Linux: `$XDG_DATA_HOME/zed` o `~/.local/share/zed`, respetando `FLATPAK_XDG_DATA_HOME`; macOS: `~/Library/Application Support/Zed`; Windows: `%LOCALAPPDATA%\Zed`). Cada hilo del agente es una fila cuyo blob comprimido con zstd (las filas antiguas son JSON plano) contiene un `cumulative_token_usage` que el propio flujo de completado del hilo acumula con una marca de agua máxima por campo — es exclusivo de caché (input + cacheRead = prompt completo), así que los buckets se corresponden directamente — y los hilos de subagente son filas independientes que nunca se pliegan en el padre, de modo que cada hilo con tokens cuenta exactamente una vez. Un hilo se tarifica con su modelo actual (uno que cambió de modelo, con el último); los ids autoalojados ausentes de la base de precios cuestan 0.00. Zed no tiene variable de entorno para redirigir el directorio de datos, así que el flag `--user-data-dir` es el punto ciego documentado. Zed no aparece en la pestaña Sesiones.

El uso de Qwen Code se lee localmente desde `<base>/projects/*/chats/*.jsonl` (más el `<base>/tmp/*/chats/*.jsonl` anterior al renombrado), donde base resuelve `$QWEN_RUNTIME_DIR`, luego `$QWEN_HOME` y luego `~/.qwen` — el `runtime_base_dir` del nivel de configuración no es alcanzable desde Tokdash y es un punto ciego documentado. Los archivos son de solo anexado, uno por sesión, y cada registro de asistente lleva el `usageMetadata` del proveedor tal cual: `promptTokenCount` incluye la caché, así que la parte cacheada se separa en su propio bucket y se cobra a la tarifa de caché, y `thoughtsTokenCount` se muestra como razonamiento. El `uuid` de cada registro es una clave estable y global a la fuente: `/branch` copia los registros del padre (mismos uuids) al archivo de la bifurcación, así que el almacén de uso asigna cada clave por la aparición más temprana y promueve una copia superviviente cuando se borra el archivo canónico. Los registros de subagente comparten el archivo de sesión y cuentan automáticamente. El coste sale de la base de precios; los registros sin modelo cuentan tokens como `unknown` a 0.00. Qwen Code no aparece en la pestaña Sesiones.

El uso de Crush se lee localmente desde `$CRUSH_DATA_DIR` (una lista separada por comas de directorios de datos, cada uno con su `crush.db`) — obligatorio, porque el directorio de datos por defecto de Crush es un `.crush` por proyecto junto al directorio de trabajo y no hay raíz global que recorrer. La base de datos usa WAL, así que Tokdash la lee por la misma ruta de copia e instantánea que ZCode. Cada sesión con tokens distintos de cero aporta una entrada, incluidas las sesiones de subagente: Crush solo pliega el coste en la sesión padre, nunca los tokens, así que el criterio de solo nivel superior de sus propias consultas de estadísticas (`parent_session_id IS NULL`) descartaría ese uso. Cada entrada se atribuye al último mensaje de asistente que no sea resumen de su sesión — una sesión con varios modelos se tarifica con el último. Tres advertencias: los contadores se asignan por paso en lugar de acumularse, así que solo guardan el tamaño de contexto de la última petición y la salida del último turno, y quedan por debajo en sesiones de varios pasos (verificado con Crush v0.91.2; nada en `crush.db` permite recuperar los totales reales); los tokens pueden ser estimaciones por recuento de caracteres cuando el proveedor informa uso cero, sin ninguna marca en la base de datos; y la separación de caché/razonamiento no se persiste. Las marcas de tiempo son segundos; las filas se agrupan por `updated_at` (último cambio), así que el total de toda la vida de una sesión cae en un solo día. `sessions.cost` se ignora; el coste sale solo de la base de precios. Crush no aparece en la pestaña Sesiones.

`tokdash setup` ofrece un paso opcional de cuota (consentimiento de red por proveedor, por defecto No, más el intervalo de consulta), y `tokdash doctor` informa del estado de la cuota: interruptor general, consentimiento por proveedor, interruptor de emergencia, intervalo efectivo y su fuente, última hora de consulta y número de instantáneas almacenadas.

Las instantáneas de cuota y su historial viven en la base de datos local de uso (`usage.sqlite3`, activada por defecto) y se **conservan indefinidamente por defecto** — fija `TOKDASH_QUOTA_RETENTION_DAYS` a un número positivo de días para podar instantáneas más antiguas. Si optas fuera de la persistencia local con `TOKDASH_USAGE_DB=0`, la pestaña Quota pierde su vía de datos principal: no se conserva historial de instantáneas, no se ejecuta el consultor de fondo, y la pestaña solo muestra resultados en memoria de un **Refrescar** manual (proveedores de red con consentimiento) durante la vida del proceso actual del servidor. Mantén la BD de uso activada (el valor por defecto) para un seguimiento de cuota normal.

## API (local)

Tokdash es un servidor HTTP local. Endpoints habituales:

- `GET /api/usage?period=today|week|month|N`
- `GET /api/usage?date_from=YYYY-MM-DD&date_to=YYYY-MM-DD`
- `GET /api/tools?period=...` (solo herramientas de codificación)
- `GET /api/openclaw?period=...` (solo OpenClaw)
- `GET /api/sessions?tool=codex|claude|opencode|pi_agent|omp|mimo|kimi|dsh|reasonix|zcode|kilocode|grok|hermes|antigravity_cli|cline&period=...` (añade `&include_review_sessions=true` para incluir sesiones de revisión/permiso de Codex, ocultas por defecto)
- `GET /api/active-time?period=...` (tiempo activo en todas las herramientas de sesión, más desglose por herramienta)
- `GET /api/quota` y `GET /api/quota/history` (instantáneas de cuota de suscripción; el refresco de red está gateado por escritura y es opt-in)
- `GET /api/stats` (calendario de contribuciones y estadísticas)

Ejemplo:
```bash
curl 'http://127.0.0.1:55423/api/usage?period=today'
```

Referencia completa de la API: [`docs/reference/API.md`](docs/reference/API.md) — esquema, parámetros y formas de respuesta de cada endpoint.

## Nota sobre la precisión del coste

Los recuentos de tokens dependen de lo que cada cliente registra localmente. Los costes se calculan por defecto desde la base de datos de precios incluida (`src/tokdash/pricing_db.json`) o desde tu sobrescritura de precios guardada del panel en `<data_dir>/pricing_db.json` si existe (la pestaña Pricing escribe allí y sustituye por completo las tarifas incluidas). En cualquier caso pueden ir por detrás del precio real del proveedor — úsalos como estimación y verifica contra tu fuente de facturación si importa.

## Retención del historial

> [!IMPORTANT]
> **Conserva tu historial.** Claude Code y Gemini CLI borran por defecto las sesiones locales de más de ~30 días, así que los meses anteriores de Tokdash pueden encogerse en silencio.

Tokdash lee los logs de sesión **locales** de cada cliente y también mantiene un índice de rendimiento SQLite local. El índice puede conservar filas que Tokdash ya haya visto, pero no puede recuperar logs eliminados antes de ser indexados, y no sustituye a conservar el historial original del cliente. Si un cliente borra logs antiguos antes de que Tokdash los sincronice, un mes pasado aún puede leerse **más bajo que cuando lo registraste por primera vez**. Solo dos clientes soportados hacen esto por defecto, y ambos son una corrección de una línea:

- **Claude Code** borra sesiones más antiguas que `cleanupPeriodDays` (**por defecto 30 días**) al arrancar. Añade esto a tu `~/.claude/settings.json` existente (y a cualquier `CLAUDE_CONFIG_DIR` alternativo):
  ```json
  { "cleanupPeriodDays": 3650 }
  ```
- **Gemini CLI** borra sesiones de más de 30 días. Desactívalo en `~/.gemini/settings.json`; si un proyecto tiene `.gemini/settings.json`, haz el mismo cambio allí porque la configuración del workspace sobreescribe la de usuario:
  ```json
  { "general": { "sessionRetention": { "enabled": false } } }
  ```

Todos los demás clientes soportados conservan el historial indefinidamente por defecto. Para la encuesta completa por cliente, detalles de la corrección y lo que el índice SQLite local sí y no preserva, ver **[docs/reference/HISTORY_RETENTION.md](docs/reference/HISTORY_RETENTION.md)**.
