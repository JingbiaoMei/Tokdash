## 기능

- **정확한 토큰 수**: 입력/출력/캐시 토큰 내역
- **상태줄 통합** *[신규]*: Claude Code(로컬 HTTP 엔드포인트에 도달할 수 있는 어떤 에이전트든)의 상태줄에 실시간 토큰 사용량 표시기를 넣습니다 — [상태줄 통합](#상태줄-통합) 참조
- **기여 캘린더**: Tokens/Cost/Messages 지표가 있는 2D 히트맵 + 3D 등각 뷰
- **세션 탐색기**: 세션별 드릴다운
- **Report 탭** *[신규]*: 본인 에이전트 활동을 주 / 월 / 연초 누적 기준으로 정리한 보고서. 상세 단계별 공유 카드 2종을 제공하며, 내보낼 때마다 밝은 색과 어두운 색 PNG 두 장을 함께 만듭니다
- **Quota 탭** *[신규]*: Codex, Claude Code, Antigravity의 구독 윈도우 바와 리셋 카운트다운. Codex 윈도우는 로컬 로그로 바로 동작하며, Codex 리셋 크레딧, 미터링 기능, 모든 Claude/Antigravity 쿼터에는 옵트인 [라이브 폴링](#쿼터-추적-선택사항)이 필요합니다
- **Companion 상태표 앱** *[신규]*: macOS 메뉴 막대나 Windows 알림 영역에서 지출과 구독 쿼터 확인 — Windows는 [Microsoft Store](https://apps.microsoft.com/detail/9ppnmpdq8b52) 제공 — [스크린샷과 다운로드](#tokdash-companion-상태표-앱)
- **멀티 서버 뷰**: 설정에서 WSL, macOS, 기타 Tokdash 서버를 추가. 임의의 선택 사용량을 합치고 쿼터는 머신별로 그룹화. [원격 접근](docs/guides/REMOTE_ACCESS.md) 참조.
- **테마와 앱 마감**: 17가지 스타일 테마, 라이트/다크 모드, PWA 설치 지원, 6개 언어 UI (English / 中文 / 日本語 / 한국어 / Español / Português)

Microsoft가 서명하고 Store를 통해 업데이트됩니다. Windows 11이 필요합니다.

**직접 다운로드** — **[Tokdash Companion 1.0.0](https://github.com/JingbiaoMei/Tokdash/releases/tag/companion-v1.0.0)**:

| 플랫폼 | 다운로드 | 요구 사항 |
|---|---|---|
| macOS | 유니버설 DMG (`arm64` + `x86_64`) | macOS 14 이상 |
| Windows | 셀프컨테인드 포트어블 ZIP (`x64`) | Windows 11. Windows on Arm은 x64 에뮬레이션으로 사용 가능 |

> [!WARNING]
> GitHub Releases 바이너리는 **서명되지 않았습니다.** macOS Gatekeeper와 Windows SmartScreen에서 미지 발신자 경고가 표시됩니다. 이 저장소에서만 다운로드하고, 포함된 `SHA256SUMS`를 확인한 후, 릴리스를 신뢰할 때에만 계속하세요. Microsoft Store 빌드는 Microsoft 서명이 되어 있어 영향을 받지 않으며, macOS 서명과 노타리제이션은 이후 릴리스에서 계획되어 있습니다.

### 설정

1. [빠른 시작](#빠른-시작)으로 **Tokdash 1.5.2 이상**을 설치하고 시작하세요.
2. Companion을 설치합니다. Windows에서는 위 Microsoft Store 링크를 사용하세요. 직접 다운로드의 경우, 자신의 플랫폼용 에셋을 받아 `SHA256SUMS`와 대조하여 검증하세요.
3. 직접 다운로드의 경우: macOS에서는 DMG를 열어 `TokdashCompanion`을(를) Applications로 드래그하고, Windows에서는 ZIP을 안정적인 디렉터리에 해제한 뒤 `TokdashCompanion.exe`를 실행하세요.
4. Companion은 기본적으로 `http://127.0.0.1:55423`에 연결됩니다. 설정을 열면 프라이빗 Tailscale Serve URL을 포함한 명시적 Tokdash 엔드포인트를 추가, 테스트, 이름 붙이기, 활성화, 제거할 수 있습니다.

Companion은 사용자가 구성한 Tokdash 엔드포인트에만 접촉합니다. 저쿼터 알림과 로그인 시 자동 실행은 모두 옵트인으로 기본값은 꺼져 있습니다. 체크섬, 업데이트, 제거 안내는 [companion 릴리스 가이드](companion/docs/RELEASE.md)를 참조하세요.

## 빠른 시작

### 플랫폼 지원

- **Linux (WSL2 포함):** 지원
- **macOS:** 지원
- **Windows (네이티브):** 실험적

### 사전 요구 사항

- Python **3.10 이상**
- [지원 클라이언트](docs/reference/SUPPORTED_CLIENTS.md)가 하나 이상 설치되어 있어야 함

### 설치

권장되는 격리 설치:

```bash
pipx install tokdash
```

pipx를 사용하지 않는다면:

```bash
python3 -m pip install --user tokdash
```

### 첫 실행

온보딩 마법사를 실행하세요:

```bash
tokdash setup
```

마법사는 플랫폼이 지원하는 경우 되돌릴 수 있는 사용자 수준 백그라운드 서비스를 구성한 뒤 대시보드 URL(기본: `http://127.0.0.1:55423`)을 표시합니다. 지원되는 서비스 매니저가 없으면 설정 상태를 기록하고 포어그라운드 실행 안내를 표시합니다. localhost 우선 기본값을 사용하며, 로컬 서비스에 `sudo`가 필요 없고, 나중에 `--purge`로 언설치하지 않는 한 사용량 히스토리를 유지합니다.

모든 네트워크 인터페이스에 쓰기 비활성화 상태로 대시보드를 명시적으로 노출하려면 `tokdash setup --bind 0.0.0.0`을 실행하세요. 먼저 [원격 접근 가이드](docs/guides/REMOTE_ACCESS.md)를 검토하세요.

에이전트, 스크립트, 번들에서 비대화형으로 설정하려면:

```bash
tokdash setup --auto --json
```

설정이 무엇을 바꿀지 미리 보기:

```bash
tokdash setup --dry-run
```

### 확인

```bash
tokdash doctor
```

`doctor`는 런타임, 백그라운드 서비스, 설정된 포트, 데이터 경로, 업데이트 확인 상태를 점검합니다. 자동화에는 `tokdash doctor --json`을 사용하세요.

### 업데이트 또는 제거

```bash
tokdash update       # 관리 대상 런타임을 업그레이드하고 가능하면 서비스를 재시작
tokdash uninstall    # setup이 만든 것만 정확히 되돌림. 기본적으로 사용량 히스토리 유지
```

`update`는 Tokdash가 안전하게 관리할 수 있는 설치 방식만추동합니다. 런타임이 Tokdash가 소유하지 않는 패키지 매니저로 설치된 경우, 그 환경을 건드리지 않고 정확한 수동 안내를 표시합니다. 관리 대상 런타임의 경우 `update`는 업그레이드 전후의 Tokdash 버전을 보고합니다. 버전이 바뀌지 않으면 새 패키지가 설치된 것처럼 보이게 하지 않고, 이미 그 버전임을 말합니다.

<details>
<summary>기존 설치: v1.0 이전에서 마이그레이션</summary>

온보딩 플로우 이전부터 Tokdash를 설치한 경우, 먼저 업그레이드하세요:

```bash
pipx upgrade tokdash
# 또는: python3 -m pip install --user -U tokdash
```

그다음 백그라운드 서비스 관리를 Tokdash에 맡기려면 `tokdash doctor`와 `tokdash setup`을 실행하세요. 이미 손으로 쓴 systemd나 launchd 서비스가 있으면 setup은 그것을 **묵시적으로 교체하지 않습니다**: 마커가 없는 `tokdash.service` / plist 파일은 기본적으로 거부합니다. 그 서비스를 계속 직접 관리하거나, setup 전에 제거하거나, `tokdash setup --dry-run`을 확인한 뒤 `tokdash setup --force`를 실행하세요. `--force`는 포트 `55423`을 차지하고 있지만 새 `/health` 지문을 노출하지 않는 1.0 이전 서비스도 처리합니다: 기존 `tokdash.service`를 다시 작성하고 재시작합니다. 서비스 생성을 건너뛰려면 `tokdash setup --no-service`를 사용하세요.

현재 설정이 conda/시스템/사용자 pip 인터프리터를 사용하고 있고, 향후 업그레이드를 `tokdash update`가 관리하게 하려면 서비스를 Tokdash의 setup 소유 venv로 마이그레이션하세요:

```bash
# 곧 실행할 tokdash 명령을 업그레이드. 예:
python3 -m pip install --user -U tokdash
# 또는, conda base 설치인 경우:
conda run -n base python -m pip install -U tokdash
tokdash setup --runtime venv --force
tokdash doctor
```

이로써 사용량 히스토리는 `~/.tokdash` 아래에 유지되고, 사용자 서비스는 `~/.tokdash/runtime/python-venv/bin/python -m tokdash`를 실행하도록 다시 작성되며, 이후 `tokdash update`가 해당 관리 venv를 업그레이드하고 서비스를 재시작하게 됩니다. pipx로 설치했다면 pipx 런타임을 그대로 유지한 채 `tokdash update`나 `pipx upgrade tokdash`로 업그레이드해도 됩니다.

### 원격 접근

Tokdash는 기본적으로 루프백에 바인딩된 채로 유지됩니다. 대화형 `tokdash setup`은 명시적 확인 후 Tailscale Serve를 구성할 수 있으며, Windows나 다른 tailnet 기기간에 프라이빗 HTTPS 읽기 접근을 제공합니다. 인증된 쓰기 접근이 필요하면 SSH 포워딩을 사용하세요. 명시적 `--bind 0.0.0.0`은 읽기 전용 네트워크 접근을 제공하지만, 인증되지 않은 대시보드를 도달 가능한 모든 인터페이스에 노출합니다.

설정 명령, WSL2 안내, 접근 URL, 쓰기 동작, 보안 트레이드오프는 **[`docs/guides/REMOTE_ACCESS.md`](docs/guides/REMOTE_ACCESS.md)**를 참조하세요.

### 포어그라운드 폴백

일회성 포어그라운드 프로세스만 필요할 때:

```bash
tokdash serve
```

`http://127.0.0.1:55423`을 엽니다. 기본 포트가 사용 중이면 `tokdash serve --port <port>`를 사용하세요.

런타임 선택, WSL/systemd 동작, macOS launchd, Tailscale, 번들링, 업데이트를 포함한 온보딩 전체 상세는 `tokdash setup` 도움말과 docs를 참조하세요.

## 구성

Tokdash는 **기본적으로 localhost 전용**입니다.

- `TOKDASH_HOST` (기본값: `127.0.0.1`)
- `TOKDASH_PORT` (기본값: `55423`)
- `TOKDASH_CACHE_TTL` (기본값: `600`초)
- `TOKDASH_CACHE_MAX_ENTRIES` (기본값: `256`) — 캐시된 API 응답과 키별 유휴 잠금에 상한 설정
- `TOKDASH_COMPUTE_CONCURRENCY` (기본값: `2`) — 동시 수행되는 무거운 히스토리 재파싱 상한. 초과한 콜드 요청은 서버를 포화시키는 대신 빠른 `503`을 반환
- `TOKDASH_STARTUP_WARM_JOIN_SECONDS` (기본값: `30`초) — 시작 시 워밍업 중인 키의 첫 요청이 `503`을 반환하는 대신 그 채움을 대기하는 시간. 키당 최대 1개 요청만 대기
- `TOKDASH_LIMIT_CONCURRENCY` (기본값: `64`) — uvicorn 연결 상한 (백프레셔)
- `TOKDASH_KEEPALIVE` (기본값: `5`초) — uvicorn 커널라이브 타임아웃
- `TOKDASH_ALLOW_ORIGINS` (쉼표 구분, 기본값: 비어 있음)
- `TOKDASH_ALLOW_ORIGIN_REGEX` (기본 CORS 정책은 localhost/127.0.0.1과 동일 tailnet의 Tailscale Serve 읽기를 허용. 어느 CORS 옵션을 설정해도 그 기본 정책을 대체)
- `TOKDASH_NO_RETENTION_NOTICE` (`1`로 설정하면 `tokdash serve`에서 표시되는 히스토리 보존 리마인더를 끔)
- `TOKDASH_SETUP_NO_OPEN` (`1`로 설정하면 `tokdash setup` 마지막의 선택적 브라우저 열기를 건너뜀)

세션 활성 시간 (추정):

모든 세션이 `span_ms`와 함께 `active_ms`를 보고합니다. Span은 첫 이벤트부터 마지막 이벤트까지. 활성 시간은 유휴를 빼고 계산되며, 연속 토큰 이벤트 사이의 각 간격은 유휴 상한까지만 카운트되므로 하룻밤 내내 열어둔 세션이 14시간 세션으로 읽히지 않습니다.

이는 추정치이며 API도 그렇게 명시합니다: `summary.active_time_estimated`가 `true`이고 `summary.active_time_method`가 `capped-inter-event-gap`입니다. 한계는 방법론에서 옵니다 — 이벤트 사이의 짧은 휴지는 작업과 구별할 수 없고, 상한보다 긴 단일 작업은 상한까지 잘리며, 토큰 이벤트가 하나뿐인 세션은 앞에 아무것도 없으므로 0으로 측정됩니다.

병렬 작업은 두 가지로 카운트됩니다. `active_ms`는 중복을 한 번만 카운트한 시계 시간이고, `active_ms_sum`은 중복을 합산한 값, 즉 에이전트 시간입니다. 둘 다 `summary`에 세션별로, 도구별로 나타납니다. Kimi 에이전트와 Claude 서브에이전트는 메인 에이전트와 함께 실행되며, 각각 독립 스트림으로 측정됩니다: 1분간 병렬로 일한 서브에이전트는 에이전트 시간에 1분을 더하고 시계 시간에는 아무것도 더하지 않습니다.

- `TOKDASH_ACTIVE_GAP_CAP_SECONDS` (기본값: `300`) — 초 단위 유휴 상한. 이보다 긴 간격은 상한분만 기여. 1초~6시간으로 클램프됨.

영속 사용량 DB (기본값: 켜짐):

Tokdash는 기본적으로 `~/.tokdash/usage.sqlite3`에 로컬 SQLite 인덱스를 유지합니다. 파싱된 토큰 행과 Codex/Claude/Kimi/DeepSeek Harness/Reasonix 세션 요약을 저장해, 반복되는 대시보드와 API 읽기가 모든 소스 로그를 재파싱하는 대신 인덱싱된 SQL을 사용할 수 있게 합니다. 소스 로그가 여전히 진실의 원천이며, DB는 로컬 성능 인덱스입니다. 비활성화되거나 사용할 수 없으면 라이브 파싱으로 되돌립니다.

캐시된 세션 행은 가격에 중립적입니다: 각 턴의 과금 입력(모델, 신선 입력, 캐시 읽기/쓰기, 출력)을 담고, 비용은 읽을 때 그 프로세스가 로드한 가격으로 계산됩니다. 따라서 요율을 수정하면 기가바이트 단위 로그를 다시 읽는 대신 즉시 재가격화되고, 하나의 데이터베이스를 공유하는 두 Tokdash 버전은 가격을 이유로 서로의 행을 무효화하지 않습니다. 다만 공유가 안전한 건 두 빌드 모두 같은 데이터베이스 스키마를 지원할 때뿐입니다: 스키마 마이그레이션은 전방으로만 실행되므로, 새 빌드가 파일을 마이그레이션하면 오래된 빌드는 업그레이드될 때까지 파일을 여는 것을 거부하고, 버전이 일치할 때까지 모든 캐시 읽기가 실패합니다. `tokdash doctor`는 디스크의 스키마와 실행 중 빌드가 지원하는 스키마를 나란히 보고합니다. 파서와 소스 파일 변경은 여전히 정상적으로 재파싱됩니다. 이보다 이전에 쓰인 행(로그가 사라져도 `TOKDASH_USAGE_DB_DURABLE`로 유지된 것을 포함)은 저장된 합계로 재가격화되어 같은 수치를 재현하지만, Claude나 Kimi 캐시 쓰기와 신선 입력을 구분하지는 못합니다. 그 구분을 되찾을 수 있는 건 해당 로그의 재파싱뿐입니다. Codex는 `provider/model`로 과금되고 이름만 저장하므로, 오래된 행은 재사용 대신 한 번 재파싱됩니다.

설치된 서비스의 데이터베이스가 절대 마이그레이션되지 않도록 체크아웃을 전용 데이터 디렉터리로 실행하세요:

```bash
TOKDASH_DATA_DIR=output/dev-data PYTHONPATH=src python3 main.py
```

- `TOKDASH_USAGE_DB` (기본값: `1`) — `0`, `false`, `no`, `off` 중 하나로 설정하면 영속 사용량 DB 비활성화
- `TOKDASH_DATA_DIR` (기본값: `~/.tokdash`) — Tokdash 로컬 상태의 기본 디렉터리
- `TOKDASH_USAGE_DB_PATH` (기본값: `$TOKDASH_DATA_DIR/usage.sqlite3`) — 명시적 SQLite 파일 경로
- `TOKDASH_USAGE_DB_DURABLE` (기본값: `1`) — 소스 파일이 일시적으로 사라지거나 파서가 행을 반환하지 않아도 이미 인덱싱된 행을 유지. 엄격한 소스 대체를 원하면 `0`
- `TOKDASH_USAGE_DB_WATCH` (기본값: `0`) — `1`로 설정하면 `tokdash serve` 내부에서 백그라운드 동기화 루프 실행
- `TOKDASH_USAGE_DB_WATCH_INTERVAL` (기본값: `30`초) — `tokdash db watch`와 serve 시 워치 루프의 동기화 간격

DB 유지보수 명령:

```bash
tokdash db status --pretty
tokdash db sync --pretty
tokdash db verify --verify-period today --pretty
tokdash db repair --dry-run --pretty
tokdash db resync --pretty
tokdash db watch --pretty
```

Tailscale Serve, SSH 포워딩, 명시적 네트워크 바인딩을 통한 원격 접근은 [`docs/guides/REMOTE_ACCESS.md`](docs/guides/REMOTE_ACCESS.md)를 참조하세요. 대화형 `tokdash setup`은 옵트인 후 Tailscale Serve 규칙을 구성하고 기록할 수 있습니다.

기본적으로 `tokdash serve`는 시작 시 브라우저에서 대시보드를 한 번 엽니다. 끄려면 `--no-open`을 넘기세요 (헤드리스/SSH 환경과 백그라운드 서비스 템플릿에서는 자동으로 건너뜀).

## 프라이버시 & 보안

- **텔레메트리 없음**: Tokdash는 데이터를 의도적으로 어디로도 보내지 않습니다.
- **로컬 파싱**: 사용량은 로컬 세션 파일에서 계산됩니다 ([지원 클라이언트](docs/reference/SUPPORTED_CLIENTS.md) 참조).
- **선택적 쿼터 폴링**: Quota 탭은 기본적으로 로컬 전용입니다. 제공자별 API 폴링은 탭에서 또는 `tokdash quota consent`로 활성화할 수 있으며, 로컬 CLI 자격 증명을 사용해 해당 제공자 자신의 쿼터 엔드포인트만 호출하고, 응답은 로컬 사용량 SQLite DB에 저장됩니다.
- **서버 노출**: Tokdash는 기본적으로 `127.0.0.1`에 바인딩됩니다. Tailscale Serve는 프라이빗 읽기 전용 접근을, SSH 포워딩은 인증된 쓰기 접근을, `--bind 0.0.0.0`은 모든 인터페이스에서 인증되지 않은 읽기를 명시적으로 노출합니다. [원격 접근 가이드](docs/guides/REMOTE_ACCESS.md) 참조.

### 쿼터 추적 (선택사항)

Quota 탭은 두 가지 데이터 소스로 구독 이용률 윈도우와 리셋 타이머를 표시합니다. **로컬 로그** (네트워크 불필요): Codex는 세션 파일에 자신의 쿼터를 기록하므로 Codex 5시간/주간 윈도우는 바로 동작합니다 — 다만 Codex를 사용할 때만 업데이트되고, 로그에는 리셋 크레딧이나 미터링 기능 윈도우가 포함되지 않습니다. 세션 로그의 Codex 소비량은 **크게 틀릴 수 있는 추정치**로 취급하세요: 각 세션이 마지막 조회 시점의 쿼터 스냅샷을 캐시해 이후 모든 메시지에서 그대로 재생하므로 수치가 오래될 수 있고, 리셋 경계 노이즈가 윈도우를 더 왜곡할 수도 있습니다 — Quota 탭은 이 차트를 추정치로 라벨링합니다. **라이브 폴링** (기본값: 꺼짐, 제공자별 동의): Tokdash는 CLI가 이미 가진 로그인으로 제공자 자신의 쿼터 엔드포인트를 호출합니다. 더 최신이고, Codex 리셋 크레딧과 미터링 기능을 추가하며, **정확한** Codex 소비량에는 필수이고, Claude Code, Antigravity, MiniMax, Kimi Code, SuperGrok/Grok Build의 유일한 쿼터 소스입니다:

Z.ai Coding Plan 쿼터도 라이브 폴링에서만 사용할 수 있습니다.

```bash
tokdash quota consent --codex-api on --claude-api on --antigravity-api on
tokdash quota consent --minimax-api on --kimi-api on --grok-api on --zai-api on
tokdash quota consent --credential-scan on   # 공개된 로컬 자격 증명 리더 허용
tokdash quota consent --poll-interval 30      # 백그라운드 폴링 간격: 15, 30, 60 또는 120분
tokdash quota consent --enabled off           # 마스터 스위치: 모든 쿼터 추적 끔
tokdash quota poll
tokdash quota show
```

**마스터 스위치.** `quota.enabled` (기본값: 켬)는 쿼터 관련 모든 작업 — 세션 스캔, 네트워크 폴링, 스냅샷 쓰기 — 을 일괄 켜고 끕니다. Quota 탭에서 또는 `tokdash quota consent --enabled on|off`로 토글하세요. 꺼져 있으면 (또는 `TOKDASH_QUOTA_POLL=0` 킬 스위치가 설정되면) 백그라운드 폴러가 완전히 유휴가 되고, `GET /api/quota/refresh`는 "quota tracking disabled" 오류를 반환하며, 탭은 데이터 대신 *쿼터 추적 활성화* 카드를 표시합니다. 제공자별 동의 키는 더 좁은 네트워크 전용 의미를 유지합니다.

**폴링 간격.** 백그라운드 폴러는 기본적으로 **30분마다** 스냅샷을 찍습니다. Quota 탭, `tokdash setup` 중, 또는 `tokdash quota consent --poll-interval N`에서 15/30/60/120분을 선택할 수 있으며, `config.json`에 `quota.poll_interval_minutes`로 저장됩니다. `TOKDASH_QUOTA_POLL_INTERVAL` 환경 변수(초, 하한 300)는 저장값을 오버라이드하고, 탭은 어떤 소스가 활성인지 표시합니다. 간격 변경은 서버 재시작 없이 다음 폴링 주기부터 적용됩니다. Codex 세션 인수는 증분입니다 — 역사 백필을 한 차례 한 후, 각 주기는 증가한 세션 파일만 끝에서 읽으므로(테일 읽기) 정상 상태 폴링 비용은 몇 밀리초입니다.

고정 리셋 쿼터 윈도우의 경우 폴러는 리셋 경계 근처에서도 샘플링해, 히스토리가 리셋 직전 고값과 리셋 직후 베이스라인을 확보하도록 합니다. 경계 샘플링은 기본적으로 켜져 있으며, 윈도우가 트리거한 제공자만 호출하고, 가까운 제공자 경계를 통합하며, 데몬 폴링 주기 사이 최소 300초를 유지합니다. `TOKDASH_QUOTA_BOUNDARY_POLL=0`으로 비활성화, `TOKDASH_QUOTA_BOUNDARY_POST=0`으로 리셋 후 샘플만 비활성화, 기본 120초 리드는 `TOKDASH_QUOTA_BOUNDARY_PRE_SECONDS`와 `TOKDASH_QUOTA_BOUNDARY_POST_SECONDS`로 조정할 수 있습니다.

라이브 폴링은 두 가지 독립적 결정을 요구합니다: `quota.credential_scan`은 공개된 로컬 자격 증명 스토어에 대한 읽기 전용 접근을 허용하고, 이어 각 `<provider>_api` 키가 해당 제공자의 네트워크 요청을 허용합니다. Tokdash는 네이티브 CLI 인증/설정 파일, OpenCode의 `auth.json`과 전역 제공자 설정, 활성 Claude 설정, CC Switch의 `providers` 테이블을 읽기 전용 SQLite 연결로 읽습니다. 제공자 로그, 셸 프로필, 임의의 `{file:...}` 참조는 절대 스캔하지 않습니다. MiniMax는 `mmx` 로그인 또는 Token Plan Subscription Key(`MINIMAX_TOKEN_PLAN_GLOBAL_KEY` / `MINIMAX_TOKEN_PLAN_CN_KEY`)를 받습니다. 일반 후불 키에는 Token Plan 쿼터가 보장되지 않습니다. Kimi는 Kimi Code 로그인/키(`KIMI_API_KEY`)를 받고, Moonshot Open Platform 후불 키는 받지 않습니다. SuperGrok/Grok Build 쿼터에는 `$GROK_HOME/auth.json`의 xAI OAuth 로그인이 필요합니다. 일반 xAI API 키로는 소비자 과금에 접근할 수 없습니다. macOS에서 Claude Code는 일회성 읽기 전용 키체인 승인을 요구할 수 있습니다. Tokdash는 제공자 자격 증명을 갱신하거나 쓰지 않습니다. `TOKDASH_QUOTA_POLL=0`은 모든 쿼터 추적을 위한 하드 킬 스위치입니다. `tokdash export`는 기본적으로 쿼터 데이터를 제외합니다. JSON에 포함하려면 의도적으로 `--include-quota`를 사용하세요.

Z.ai는 `$ZCODE_HOME/v2/config.json`, 지원되는 도구 설정, `ZAI_API_KEY` 또는 `Z_AI_API_KEY`의 Coding Plan 키를 허용하며 5시간/주간 크레딧 윈도우와 레거시 MCP 한도를 조회합니다.

Grok Build 토큰 사용량도 `$GROK_HOME/logs/unified.jsonl`에서 로컬로 파싱됩니다. 그 추론 레코드는 프롬프트, 캐시된 프롬프트,완성, 추론 토큰을 노출하고, Tokdash는 같은 CLI 프로세스의 모델 이벤트로 귀속하고 통상 가격 데이터베이스로 비용을 계산합니다. 모델 이벤트가 없는 레코드는 추정 가격을 지정하는 대신 건너뜁니다.

DeepSeek Harness(`dsh`) 사용량과 세션은 `$DSH_HOME/sessions/*/*/session.jsonl.zstd`(또는 비압축 `session.jsonl`)에서 로컬로 읽으며, `DSH_HOME` 기본값은 `~/.dsh`입니다. 각 로그는 이어 붙은 zstd 프레임의 시퀀스입니다. Tokdash는 모든 프레임을 디코드하고, 각 단계의 초기 사용량 청크를 확정된 메시지에 접어 이중 계산을 피하며, 포크된 세션의 상속된 프리픽스를 건너뛰어 부모-자식이 같은 토큰을 두 번 과금하지 않게 합니다.

Reasonix 사용량과 세션은 `$REASONIX_HOME`(기본값 `~/.reasonix`)에서 로컬로 읽습니다: 요청별 토큰은 일일 `stats/YYYY-MM-DD.jsonl` 로그에서, 세션 구조는 `projects/*/sessions/*.jsonl`에서. Reasonix는 `config.toml`에 이름이 올라온 제공자와 통신하므로, 각 행의 `provider/model` 페어는 통상 가격 데이터베이스로 귀속·가격화됩니다. 공개 요율이 없는 셀프호스티드 모델은 토큰을 제로 비용으로 집계합니다. Reasonix는 요청별로 사용량을 기록하고 세션 ID를 부여하지 않으므로, Session Explorer 행은 토큰 수 없이 턴, 프로젝트, 시기를 표시합니다 — 전체 합계는 Overview와 Stats에 있습니다.
ZCode 사용량은 `$ZCODE_HOME/cli/db/db.sqlite`(기본값 `~/.zcode/cli/db/db.sqlite`. `ZCODE_HOME`은 ZCode 자체 설정을 따름)에서 로컬로 읽습니다. 각 `model_usage` 행은 재시도 포함 하나의 모델 요청이며, 행의 `model_id`는 통상 가격 데이터베이스로 가격화되고, `provider_id`(예: `builtin:zai-start-plan`)는 라벨로 유지됩니다. ZCode의 `input_tokens`는 캐시/비캐시 프롬프트 토큰을 합산해서 세므로, 캐시 부분은 별도 버킷으로 분리해 캐시 요율을 적용하고, 추론 토큰은 출력과 분리해 표시하되 출력 요율로 과금됩니다. ZCode는 Sessions 탭에도 나타납니다: 턴은 같은 데이터베이스에서 읽히고 같은 규칙으로 (턴, 모델) 단위로 과금되며, 최상위 세션만 포함합니다. 과금 토큰을 만들지 않은 턴도 측정된 시간을 해당 도구의 활성 시간에 가산합니다. ZCode의 Coding Plan 쿼터는 원격 계정 데이터이며 로컬 파서의 범위 밖입니다.

Coding Plan 쿼터는 별도로 동의한 Z.ai 라이브 폴러를 통해 사용할 수 있습니다.

WorkBuddy 사용량은 `~/.workbuddy-ai/projects/*/*.jsonl` 트랜스크립트에서 로컬로 읽습니다(`WORKBUDDY_DATA_DIR`은 쉼표 구분 루트 목록을 받아 다른 스토어, 예: WSL의 Windows 데이터 디렉터리 등을 지정할 수 있음). 각 어시스턴트 메시지 행은 하나의 모델 호출이며, `prompt_tokens` 안의 캐시 부분은 별도 버킷으로 분리해 캐시 요율을 적용하고, 추론 토큰은 출력과 분리해 표시하되 출력 요율로 과금됩니다. 모델 ID는 그대로 유지됩니다: 명시적 ID(예: gpt-5.5)는 통상 가격 데이터베이스로 가격화되고, Auto 라우터 별칭(`default-model`)은 가격 DB에 없으므로 비용 0.00입니다. 턴별 `credit` 값은 메타데이터로만 저장되며 비용에 영향을 주지 않습니다. Sessions 탭은 같은 루트에서 같은 트랜스크립트 행(과금 대상 어시스턴트 1행 = 1턴)을 읽습니다.

Qoder 사용량은 두 곳에서 로컬로 읽습니다: IDE의 SQLite 데이터베이스(IDE 데이터 디렉터리 아래 `SharedClientCache/cache/db/local.db`. Windows와 WSL에서는 QoderCN 빌드가 국제판보다 우선)와 CLI JSONL 로그(`~/.qoder`와 `~/.qoder-cn`, 그리고 `QODER_CONFIG_DIR`과 쉼표 구분 `QODER_CLI_HOME`). IDE 쪽에서는 모든 롤의 `chat_message` 행이 모두 카운트되고, 캐시 부분은 프롬프트 토큰에서 별도 버킷으로 분리되며, 모델은 `model_key`(라우터 이름이 없으면 `auto`)에서 옵니다. CLI 쪽에서는 각 요청의 트랜스크립트 과금 기록이 모든 루트에서 세그먼트 토큰 기록과 병합됩니다: 제공자 크레딧을 가진 행은 제공자 보고 비용을 권위로 유지(추정 크레딧 1개당 $0.01로 환산, `QODER_USD_PER_CREDIT`이 추정을 오버라이드하며 절대 재가격화되지 않음), 토큰만 있는 행은 통상 가격 데이터베이스로 가격화됩니다. 입력 토큰이 없는 기록은 알려진 컨텍스트 윈도우에 대한 `context_usage_ratio`로 복원합니다 — 기본 `auto`는 180,000, `QODER_CLI_CONTEXT_WINDOW`이 명시 설정된 뒤로는 모든 모델. Qoder IDE는 Sessions 탭에 표시됩니다: 같은 `chat_message` 행(모든 롤, 해석 가능한 행 1개 = 턴 1개)을 같은 DB의 임시 디렉터리 스냅샷에서 읽습니다.

Zed 사용량은 OS별 Zed 데이터 디렉터리 아래의 `threads/threads.db`에서 로컬로 읽습니다(Linux: `$XDG_DATA_HOME/zed` 또는 `~/.local/share/zed`, `FLATPAK_XDG_DATA_HOME` 반영; macOS: `~/Library/Application Support/Zed`; Windows: `%LOCALAPPDATA%\Zed`). 에이전트 스레드 하나가 한 행이며, zstd로 압축된 blob(구형 행은 일반 JSON)이 `cumulative_token_usage`를 담습니다. 이 값은 스레드 자신의 완성 스트림이 필드별 최고 수위로 누적한 것으로, 캐시 배타적(input + cacheRead가 전체 프롬프트)이라 버킷이 그대로 대응됩니다. 서브에이전트 스레드는 별도 행이며 부모로 접히지 않으므로, 토큰이 있는 각 스레드는 정확히 한 번만 계산됩니다. 스레드는 현재 모델(모델을 바꾼 경우 마지막 모델)로 가격이 매겨지고, 가격 DB에 없는 자체 호스팅 ID는 비용 0.00입니다. Zed에는 데이터 디렉터리를 바꾸는 환경 변수가 없어 `--user-data-dir` 플래그가 문서화된 사각지대입니다. Zed는 Sessions 탭에 나타나지 않습니다.

Qwen Code 사용량은 `<base>/projects/*/chats/*.jsonl`(그리고 이름 변경 전의 `<base>/tmp/*/chats/*.jsonl`)에서 로컬로 읽습니다. base는 `$QWEN_RUNTIME_DIR`, 그다음 `$QWEN_HOME`, 그다음 `~/.qwen` 순으로 결정됩니다 — 설정 수준의 `runtime_base_dir`은 Tokdash에서 접근할 수 없으며 문서화된 사각지대입니다. 파일은 추가 전용이고 세션당 하나이며, 각 어시스턴트 레코드는 제공자의 `usageMetadata`를 그대로 담습니다: `promptTokenCount`는 캐시를 포함하므로 캐시 몫은 별도 버킷으로 분리해 캐시 요율로 과금하고, `thoughtsTokenCount`는 추론으로 표시합니다. 각 레코드의 `uuid`는 소스 전역에서 안정적인 키입니다: `/branch`는 부모의 레코드(같은 uuid)를 포크 파일로 복사하므로, 사용량 저장소는 가장 이른 출현으로 키 소유를 정하고 정규 파일이 삭제되면 살아남은 사본을 승격시킵니다. 서브에이전트 레코드는 세션 파일을 공유하며 자동으로 계산됩니다. 비용은 가격 DB에서만 나오고, 모델이 없는 레코드는 `unknown`으로 0.00 처리합니다. Qwen Code는 Sessions 탭에 나타나지 않습니다.

Crush 사용량은 `$CRUSH_DATA_DIR`(각각 `crush.db`를 담은 데이터 디렉터리의 쉼표 구분 목록)에서 로컬로 읽습니다 — 필수입니다. Crush의 기본 데이터 디렉터리는 작업 디렉터리 옆의 프로젝트별 `.crush`여서 훑을 전역 루트가 없기 때문입니다. 데이터베이스는 WAL 모드라 ZCode와 같은 복사·스냅샷 경로로 읽습니다. 토큰이 0이 아닌 세션마다 항목 하나이며 서브에이전트 세션도 포함합니다: Crush는 부모 세션에 비용만 접고 토큰은 접지 않으므로, Crush 자체 통계 쿼리가 쓰는 최상위 전용 조건(`parent_session_id IS NULL`)으로는 그 사용량이 누락됩니다. 각 항목은 해당 세션의 마지막 비요약 어시스턴트 메시지에 귀속됩니다 — 여러 모델을 쓴 세션은 마지막 모델로 가격이 매겨집니다. 주의할 점이 셋 있습니다: 카운터는 누적이 아니라 단계별로 대입되므로 마지막 요청의 컨텍스트 크기와 마지막 턴의 출력만 담고 있어 다단계 세션에서는 실제보다 낮게 나옵니다(Crush v0.91.2로 확인했으며, `crush.db`에는 실제 합계를 복원할 수단이 없습니다). 제공자가 사용량 0을 보고하면 토큰이 문자 수 기반 추정치일 수 있고 DB에는 아무 표시가 없습니다. 그리고 캐시/추론 분리는 저장되지 않습니다. 타임스탬프는 초 단위이며 행은 `updated_at`(마지막 변경)으로 묶이므로 세션 전체 기간의 합계가 하루에 몰립니다. `sessions.cost`는 무시하고 비용은 가격 DB에서만 구합니다. Crush는 Sessions 탭에 나타나지 않습니다.

`tokdash setup`은 선택적 쿼터 단계(제공자별 네트워크 동의, 기본 No, 그리고 폴링 간격)를 제공하며, `tokdash doctor`는 쿼터 상태를 보고합니다: 마스터 스위치, 제공자별 동의, 킬 스위치, 유효 간격과 그 소스, 마지막 폴링 시각, 저장된 스냅샷 수.

쿼터 스냅샷과 그 히스토리는 로컬 사용량 데이터베이스(`usage.sqlite3`, 기본값: 켜짐)에 있으며, **기본값으로는 무기한 유지**됩니다 — 오래된 스냅샷을 정리하려면 `TOKDASH_QUOTA_RETENTION_DAYS`를 일 단위의 양수로 설정하세요. `TOKDASH_USAGE_DB=0`로 로컬 영속을 옵트아웃하면 Quota 탭은 주요 데이터 경로를 잃습니다: 스냅샷 히스토리가 유지되지 않고, 백그라운드 폴러가 동작하지 않으며, 탭은 수동 **Refresh**(동의한 네트워크 제공자)의 결과를 현재 서버 프로세스 수명 동안 메모리에서만 표시합니다. 정상적인 쿼터 추적을 위해 사용량 DB를 켜 두세요(기본값).

## API (로컬)

Tokdash는 로컬 HTTP 서버입니다. 흔한 엔드포인트:

- `GET /api/usage?period=today|week|month|N`
- `GET /api/usage?date_from=YYYY-MM-DD&date_to=YYYY-MM-DD`
- `GET /api/tools?period=...` (코딩 도구만)
- `GET /api/openclaw?period=...` (OpenClaw만)
- `GET /api/sessions?tool=codex|claude|opencode|pi_agent|omp|mimo|kimi|dsh|reasonix|zcode|kilocode|grok|hermes|antigravity_cli|cline&period=...` (Codex 리뷰/허용 세션을 포함하려면 `&include_review_sessions=true` 추가, 기본적으로 숨김)
- `GET /api/active-time?period=...` (모든 세션 도구의 활성 시간 + 도구별 내역)
- `GET /api/quota`와 `GET /api/quota/history` (구독 쿼터 스냅샷. 네트워크 새로고침는 쓰기 게이트되고 옵트인)
- `GET /api/stats` (기여 캘린더 & 통계)

예:
```bash
curl 'http://127.0.0.1:55423/api/usage?period=today'
```

완전한 API 참조: [`docs/reference/API.md`](docs/reference/API.md) — 모든 엔드포인트의 스키마, 파라미터, 응답 형태.

## 비용 정확도 안내

토큰 수는 각 클라이언트가 로컬에 로그하는 내용에 따라 달라집니다. 비용은 기본적으로 번들된 가격 데이터베이스(`src/tokdash/pricing_db.json`), 있으면 저장된 대시보드 가격 오버라이드(`<data_dir>/pricing_db.json`. Pricing 탭이 여기에 쓰고 번들 요율을 완전히 대체)에서 계산됩니다. 어느 쪽이든 실제 제공자 가격보다 늦을 수 있습니다 — 추정치로 쓰고, 중요하면 청구 출처와 대조하세요.

## 히스토리 보존

> [!IMPORTANT]
> **히스토리를 보존하세요.** Claude Code와 Gemini CLI는 기본적으로 약 30일 이전의 로컬 세션을 삭제하므로, Tokdash의 이전 달들이 조용히 줄어듭니다.

Tokdash는 각 클라이언트의 **로컬** 세션 로그를 읽고 로컬 SQLite 성능 인덱스도 유지합니다. 인덱스는 Tokdash가 이미 본 행을 유지할 수 있지만, 인덱싱되기 전에 삭제된 로그를 되찾을 수는 없으며, 원본 클라이언트 히스토리를 보존하는 대체재도 아닙니다. 클라이언트가 Tokdash가 동기화하기 전에 오래된 로그를 삭제하면, 과거의 달이 **처음 기록했을 때보다 낮게** 읽힐 수 있습니다. 기본적으로 이렇게 하는 지원 클라이언트는 두 곳뿐이고, 둘 다 한 줄로 수정됩니다:

- **Claude Code**는 시작 시 `cleanupPeriodDays`(**기본값 30일**)보다 오래된 세션을 삭제합니다. 기존 `~/.claude/settings.json`(그리고 대체 `CLAUDE_CONFIG_DIR`이 있으면)에 이것을 추가하세요:
  ```json
  { "cleanupPeriodDays": 3650 }
  ```
- **Gemini CLI**는 30일 이상된 세션을 삭제합니다. `~/.gemini/settings.json`에서 비활성화하세요. 프로젝트에 `.gemini/settings.json`이 있으면 워크스페이스 설정이 사용자 설정보다 우선하므로 거기서도 같은 변경을 하세요:
  ```json
  { "general": { "sessionRetention": { "enabled": false } } }
  ```

나머지 모든 지원 클라이언트는 기본적으로 히스토리를 무기한 유지합니다. 클라이언트별 전체 조사, 수정 상세, 로컬 SQLite 인덱스가 보존하는/보존하지 않는 것의 전체는 **[docs/reference/HISTORY_RETENTION.md](docs/reference/HISTORY_RETENTION.md)**를 참조하세요.
