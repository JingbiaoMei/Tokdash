## Funcionalidades

- **Contagem exata de tokens**: detalhamento de tokens de entrada/saída/cache
- **Integração com statusline** *[novo]*: coloque um indicador de uso de tokens ao vivo na statusline do Claude Code (ou qualquer agente que consiga acionar um endpoint HTTP local) — veja [Integração com statusline](#integração-com-statusline)
- **Calendário de contribuições**: heatmap 2D + visão isométrica 3D com métricas de Tokens/Cost/Messages
- **Explorador de sessões**: detalhamento por sessão
- **Aba Quota** *[novo]*: barras de janela de assinatura com contagem regressiva de reset para Codex, Claude Code e Antigravity. As janelas do Codex funcionam direto dos logs locais; créditos de reset do Codex, recursos medidos e todas as cotas do Claude/Antigravity exigem [polling ao vivo](#acompanhamento-de-cota-opcional) opt-in
- **App de barra de status Companion** *[novo]*: veja gasto e cota de assinatura na barra de menu do macOS ou na área de notificação do Windows — para Windows na [Microsoft Store](https://apps.microsoft.com/detail/9ppnmpdq8b52) — [capturas e downloads](#tokdash-companion-app-de-barra-de-status)
- **Visões multi-servidor**: adicione servidores Tokdash de WSL, macOS e outros nas Configurações; combine o uso de qualquer seleção mantendo a cota agrupada por máquina. Veja [acesso remoto](docs/guides/REMOTE_ACCESS.md).
- **Temas e acabamento do app**: 17 temas de estilo, modo claro/escuro, suporte a instalação PWA e UI em 6 idiomas (English / 中文 / 日本語 / 한국어 / Español / Português)

### Configuração

1. Instale e inicie o **Tokdash 1.5.2 ou mais novo** usando o [Início rápido](#início-rápido).
2. Instale o companion. No Windows, use o link da Microsoft Store acima. Para download direto, obtenha o asset da sua plataforma e verifique contra o `SHA256SUMS`.
3. A partir de um download direto: no macOS, abra o DMG e arraste `TokdashCompanion` para Aplicativos; no Windows, extraia o ZIP para um diretório estável e execute `TokdashCompanion.exe`.
4. O companion se conecta a `http://127.0.0.1:55423` por padrão. Abra as configurações dele para adicionar, testar, nomear, habilitar ou remover endpoints Tokdash explícitos, incluindo URLs privadas do Tailscale Serve.

O companion só contata os endpoints Tokdash que você configurar. Notificações de cota baixa e inicialização no login são opt-in e desabilitadas por padrão. Veja o [guia de release do companion](companion/docs/RELEASE.md) para instruções de checksum, atualização e remoção.

## Início rápido

### Suporte por plataforma

- **Linux (incluindo WSL2):** suportado
- **macOS:** suportado
- **Windows (nativo):** experimental

### Pré-requisitos

- Python **3.10 ou superior**
- Um ou mais [clientes suportados](docs/reference/SUPPORTED_CLIENTS.md) instalados

### Instalação

Instalação isolada recomendada:

```bash
pipx install tokdash
```

Se você não usa pipx:

```bash
python3 -m pip install --user tokdash
```

### Primeira execução

Execute o assistente de onboarding:

```bash
tokdash setup
```

O assistente configura um serviço em segundo plano reversível em nível de usuário quando a plataforma suporta, e então imprime a URL do painel (padrão: `http://127.0.0.1:55423`). Se não houver nenhum gerenciador de serviços suportado, ele registra o estado da configuração e imprime orientações de execução em primeiro plano. Usa padrões localhost-first, não requer `sudo` para o serviço local e mantém seu histórico de uso, a menos que você desinstale depois com `--purge`.

Para expor o painel explicitamente em todas as interfaces de rede com gravação desabilitada, execute `tokdash setup --bind 0.0.0.0`; revise primeiro o [guia de acesso remoto](docs/guides/REMOTE_ACCESS.md).

Para uma configuração não interativa a partir de um agente, script ou bundle:

```bash
tokdash setup --auto --json
```

Para pré-visualizar o que a configuração mudaria:

```bash
tokdash setup --dry-run
```

### Verificar

```bash
tokdash doctor
```

O `doctor` verifica o runtime, o serviço em segundo plano, a porta configurada, os caminhos de dados e o estado da verificação de atualizações. Use `tokdash doctor --json` para automação.

### Atualizar ou remover

```bash
tokdash update       # faz upgrade do runtime gerenciado e reinicia o serviço quando possível
tokdash uninstall    # reverte exatamente o que o setup criou; mantém o histórico de uso por padrão
```

O `update` só dirige métodos de instalação que o Tokdash pode gerenciar com segurança. Se o seu runtime foi instalado por um gerenciador de pacotes que o Tokdash não controla, ele imprime as orientações manuais exatas em vez de modificar esse ambiente. Para runtimes gerenciados, o `update` reporta a versão do Tokdash antes e depois do upgrade; se a versão não mudar, ele diz que o Tokdash já está nessa versão em vez de sugerir que um novo pacote foi instalado.

<details>
<summary>Instalações existentes: migração de antes da v1.0</summary>

Se você instalou o Tokdash antes do fluxo de onboarding, faça upgrade primeiro:

```bash
pipx upgrade tokdash
# ou: python3 -m pip install --user -U tokdash
```

Depois execute `tokdash doctor` e `tokdash setup` quando quiser que o Tokdash gerencie o serviço em segundo plano. Se você já tem um serviço systemd ou launchd escrito à mão, o setup **não** o substitui em silêncio: por padrão ele recusa arquivos `tokdash.service` / plist sem marca. Continue gerenciando esse serviço você mesmo, remova-o antes do setup, ou execute `tokdash setup --force` depois de conferir `tokdash setup --dry-run`. O `--force` também lida com serviços anteriores a 1.0 que já ocupam a porta `55423` mas não expõem a nova impressão digital `/health`: ele reescreve e reinicia o `tokdash.service` existente. Use `tokdash setup --no-service` para pular a criação do serviço.

Se a sua configuração atual usa um interpretador conda/sistema/pip de usuário e você quer que o `tokdash update` gerencie futuros upgrades, migre o serviço para o venv de propriedade do setup do Tokdash:

```bash
# Faça upgrade do comando tokdash que você está prestes a executar, por exemplo:
python3 -m pip install --user -U tokdash
# ou, para uma instalação no conda base:
conda run -n base python -m pip install -U tokdash
tokdash setup --runtime venv --force
tokdash doctor
```

Isso mantém seu histórico de uso em `~/.tokdash`, reescreve o serviço de usuário para executar `~/.tokdash/runtime/python-venv/bin/python -m tokdash` e permite que futuros `tokdash update` façam upgrade desse venv gerenciado e reiniciem o serviço. Se você instalou com pipx, pode manter o runtime do pipx e fazer upgrade com `tokdash update` ou `pipx upgrade tokdash`.

</details>

### Acesso remoto

O Tokdash permanece vinculado ao loopback por padrão. O `tokdash setup` interativo pode configurar o Tailscale Serve após confirmação explícita, fornecendo acesso HTTPS privado somente de leitura do Windows ou de outro dispositivo do tailnet. Use encaminhamento SSH quando precisar de acesso de gravação autenticado. Um `--bind 0.0.0.0` explícito fornece acesso de rede somente de leitura, mas expõe o painel não autenticado em toda interface alcançável.

Veja **[`docs/guides/REMOTE_ACCESS.md`](docs/guides/REMOTE_ACCESS.md)** para comandos de configuração, orientação WSL2, URLs de acesso, comportamento de gravação e trade-offs de segurança.

### Alternativa em primeiro plano

Se você só quer um processo pontual em primeiro plano:

```bash
tokdash serve
```

Abra `http://127.0.0.1:55423`. Use `tokdash serve --port <porta>` se a porta padrão estiver ocupada.

Para todos os detalhes do onboarding, incluindo escolhas de runtime, comportamento WSL/systemd, launchd do macOS, Tailscale, bundle e atualizações, consulte o help do `tokdash setup` e a documentação.

### Digest do OpenClaw (relatórios agendados)

## Configuração

O Tokdash é **somente localhost por padrão**.

- `TOKDASH_HOST` (padrão: `127.0.0.1`)
- `TOKDASH_PORT` (padrão: `55423`)
- `TOKDASH_CACHE_TTL` (padrão: `600` segundos)
- `TOKDASH_CACHE_MAX_ENTRIES` (padrão: `256`) — limita respostas de API em cache e seus travamentos de ociosidade por chave
- `TOKDASH_COMPUTE_CONCURRENCY` (padrão: `2`) — limite de reparseios pesados de histórico simultâneos; requisições frias excedentes retornam um `503` rápido em vez de saturar o servidor sob carga
- `TOKDASH_STARTUP_WARM_JOIN_SECONDS` (padrão: `30` segundos) — quanto tempo a primeira requisição de uma chave ainda em aquecimento na inicialização espera por esse preenchimento em vez de retornar `503`; no máximo uma requisição por chave espera
- `TOKDASH_LIMIT_CONCURRENCY` (padrão: `64`) — limite de conexões do uvicorn (backpressure)
- `TOKDASH_KEEPALIVE` (padrão: `5` segundos) — timeout keep-alive do uvicorn
- `TOKDASH_ALLOW_ORIGINS` (separado por vírgulas, padrão: vazio)
- `TOKDASH_ALLOW_ORIGIN_REGEX` (a política CORS padrão permite localhost/127.0.0.1 e leituras do Tailscale Serve do mesmo tailnet; definir qualquer opção CORS substitui essa política padrão)
- `TOKDASH_NO_RETENTION_NOTICE` (defina `1` para silenciar o lembrete de retenção de histórico impresso no `tokdash serve`)
- `TOKDASH_SETUP_NO_OPEN` (defina `1` para pular a abertura opcional do navegador no final do `tokdash setup`)

Tempo ativo de sessão (estimado):

Cada sessão reporta `active_ms` ao lado de `span_ms`. Span é do primeiro ao último evento; o tempo ativo subtrai a ociosidade contando cada intervalo entre eventos de tokens consecutivos apenas até um limite de ociosidade, de modo que uma sessão deixada aberta a noite toda não é mais lida como uma sessão de 14 horas.

É uma estimativa, e a API diz isso: `summary.active_time_estimated` é `true` e `summary.active_time_method` é `capped-inter-event-gap`. Os limites vêm do método — uma pausa curta entre eventos é indistinguível de trabalho, uma operação única mais longa que o limite é truncada nele, e uma sessão com um único evento de tokens mede zero porque nada a precede.

Trabalho concorrente é contado de duas formas. `active_ms` é tempo de relógio, com sobreposição contada uma vez; `active_ms_sum` soma a sobreposição, ou seja, tempo de agente. Ambos aparecem por sessão e por ferramenta em `summary`. Agentes Kimi e subagentes Claude rodam ao lado do agente principal, e cada um é cronometrado como seu próprio fluxo: um subagente trabalhando um minuto em paralelo adiciona um minuto de tempo de agente e nenhum de tempo de relógio.

- `TOKDASH_ACTIVE_GAP_CAP_SECONDS` (padrão: `300`) — limite de ociosidade em segundos; intervalos mais longos contribuem apenas o limite. Limitado a 1s–6h.

Banco de uso persistente (ligado por padrão):

O Tokdash mantém por padrão um índice SQLite local em `~/.tokdash/usage.sqlite3`. Ele armazena linhas de tokens analisadas e resumos de sessões de Codex/Claude/Kimi/DeepSeek Harness/Reasonix para que leituras repetidas do painel e da API usem SQL indexado em vez de reparsear todos os logs de origem. Os logs de origem continuam sendo a fonte de verdade; o banco é um índice de desempenho local, e o Tokdash volta ao parsing ao vivo se ele estiver desabilitado ou indisponível.

Linhas de sessão em cache são neutras em preço: elas guardam as entradas de faturamento de cada turno (modelo, entrada fresca, leituras e escrituras de cache, saída), e o custo é calculado quando são lidas, com a tabela de preços que aquele processo tiver carregado. Editar uma taxa, portanto, repricinga instantaneamente em vez de reler gigabytes de logs, e duas versões do Tokdash compartilhando um banco não invalidam as linhas uma da outra por preço. Compartilhar só é seguro enquanto ambos os builds suportarem o mesmo esquema de banco de dados: migrações de esquema rodam apenas para frente, então uma vez que o build mais novo migra o arquivo, o antigo se recusa a abri-lo até ser atualizado, e toda leitura em cache falha até as versões coincidirem. O `tokdash doctor` reporta o esquema em disco ao lado do que o build em execução suporta. Mudanças de parser e de arquivo de origem ainda reparseiam normalmente. Linhas escritas antes disso (incluindo as mantidas pelo `TOKDASH_USAGE_DB_DURABLE` após o log sumir) repricingam a partir dos totais armazenados, o que reproduz o mesmo número mas não consegue separar uma escrita de cache do Claude ou Kimi de entrada fresca; apenas um reparseo desses logs pode restaurar essa distinção. O Codex cobra como `provider/model` e armazena o nome puro, então suas linhas mais antigas são reparseadas uma vez em vez de reutilizadas.

Execute um checkout contra seu próprio diretório de dados para que ele nunca migre o banco do serviço instalado:

```bash
TOKDASH_DATA_DIR=output/dev-data PYTHONPATH=src python3 main.py
```

- `TOKDASH_USAGE_DB` (padrão: `1`) — defina `0`, `false`, `no` ou `off` para desabilitar o banco de uso persistente
- `TOKDASH_DATA_DIR` (padrão: `~/.tokdash`) — diretório base do estado local do Tokdash
- `TOKDASH_USAGE_DB_PATH` (padrão: `$TOKDASH_DATA_DIR/usage.sqlite3`) — caminho explícito do arquivo SQLite
- `TOKDASH_USAGE_DB_DURABLE` (padrão: `1`) — mantém linhas já indexadas se um arquivo de origem sumir temporariamente ou um parser não retornar linhas; defina `0` para substituição estrita de origem
- `TOKDASH_USAGE_DB_WATCH` (padrão: `0`) — defina `1` para rodar um loop de sincronização em segundo plano dentro do `tokdash serve`
- `TOKDASH_USAGE_DB_WATCH_INTERVAL` (padrão: `30` segundos) — intervalo de sincronização do `tokdash db watch` e do loop de observação durante o serve

Comandos de manutenção do banco:

```bash
tokdash db status --pretty
tokdash db sync --pretty
tokdash db verify --verify-period today --pretty
tokdash db repair --dry-run --pretty
tokdash db resync --pretty
tokdash db watch --pretty
```

Para acesso remoto através do Tailscale Serve, encaminhamento SSH ou vínculo de rede explícito, veja
[`docs/guides/REMOTE_ACCESS.md`](docs/guides/REMOTE_ACCESS.md). O `tokdash setup` interativo pode configurar e
registrar a regra do Tailscale Serve após você optar por isso.

Por padrão o `tokdash serve` abre o painel no seu navegador uma vez na inicialização. Passe `--no-open` para desabilitar (também é pulado automaticamente em ambientes headless/SSH e nos templates de serviço em segundo plano).

## Privacidade & segurança

- **Sem telemetria**: o Tokdash não envia seus dados a lugar nenhum intencionalmente.
- **Parsing local**: o uso é calculado a partir de arquivos de sessão locais (veja [clientes suportados](docs/reference/SUPPORTED_CLIENTS.md)).
- **Polling de cota opcional**: a aba Quota é somente local por padrão. O polling de API por provedor pode ser ativado da aba ou com `tokdash quota consent`; usa suas credenciais locais de CLI apenas para chamar o endpoint de cota daquele provedor, e armazena as respostas no banco SQLite local de uso.
- **Exposição do servidor**: o Tokdash se vincula a `127.0.0.1` por padrão. O Tailscale Serve fornece acesso privado somente de leitura, o encaminhamento SSH fornece acesso de gravação autenticado, e `--bind 0.0.0.0` expõe explicitamente leituras não autenticadas em toda interface. Veja o [guia de acesso remoto](docs/guides/REMOTE_ACCESS.md).

### Acompanhamento de cota (opcional)

A aba Quota mostra janelas de utilização de assinatura e cronômetros de reset, a partir de duas fontes de dados. **Logs locais** (sem rede): o Codex registra sua própria cota em arquivos de sessão, então as janelas de 5 horas/semana do Codex funcionam de cara — mas só são atualizadas quando você usa o Codex, e os logs nunca contêm créditos de reset ou janelas de recursos medidos. Trate o consumo do Codex dos logs de sessão como uma **estimativa que pode estar materialmente errada**: cada sessão faz cache de seu snapshot de cota na última consulta e o reproduz inalterado em toda mensagem posterior, então os números podem estar desatualizados, e o ruído na fronteira de reset pode ocasionalmente distorcer ainda mais uma janela — a aba Quota rotula esses gráficos como estimados. **Polling ao vivo** (desligado por padrão, consentimento por provedor): o Tokdash chama o endpoint de cota do próprio provedor com o login que sua CLI já tem. É mais fresco, adiciona créditos de reset do Codex e recursos medidos, é necessário para o consumo do Codex **exato**, e é a única fonte de cota para Claude Code, Antigravity, MiniMax, Kimi Code e SuperGrok/Grok Build:

A cota do Z.ai Coding Plan também está disponível apenas pelo polling ao vivo.

```bash
tokdash quota consent --codex-api on --claude-api on --antigravity-api on
tokdash quota consent --minimax-api on --kimi-api on --grok-api on --zai-api on
tokdash quota consent --credential-scan on   # permita os leitores locais de credenciais divulgados
tokdash quota consent --poll-interval 30      # cadência de polling em segundo plano: 15, 30, 60 ou 120 min
tokdash quota consent --enabled off           # interruptor geral: desliga TODO o acompanhamento de cota
tokdash quota poll
tokdash quota show
```

**Interruptor geral.** `quota.enabled` (ligado por padrão) liga ou desliga *todo* o trabalho de cota — varredura de sessões, polling de rede e escrita de snapshots. Alterne da aba Quota ou com `tokdash quota consent --enabled on|off`. Quando está desligado (ou o kill switch `TOKDASH_QUOTA_POLL=0` está definido), o poler em segundo plano fica completamente ocioso, `GET /api/quota/refresh` retorna um erro "quota tracking disabled" e a aba mostra um cartão de *ativar acompanhamento de cota* em vez de dados. As chaves de consentimento por provedor mantêm seu significado mais estreito, somente de rede.

**Intervalo de polling.** O poler em segundo plano faz snapshot a cada **30 minutos** por padrão. Escolha 15/30/60/120 minutos da aba Quota, durante o `tokdash setup`, ou com `tokdash quota consent --poll-interval N`; é salvo como `quota.poll_interval_minutes` no `config.json`. A variável de ambiente `TOKDASH_QUOTA_POLL_INTERVAL` (segundos, piso 300) sobrescreve o valor salvo, e a aba mostra qual fonte está ativa. Mudanças de intervalo se aplicam no próximo ciclo de polling sem reiniciar o servidor. A ingestão de sessões do Codex é incremental — após um backfill único do seu histórico, cada ciclo só lê o fim dos arquivos de sessão que cresceram, então um polling em estado estável custa milissegundos de um dígito.

Para janelas de cota com reset fixo, o poler também amostra perto da fronteira de reset para que o histórico capture o alto pré-reset e a linha de base pós-reset. A amostragem de fronteiras está ligada por padrão, chama apenas o provedor cuja janela a disparou, agrega fronteiras próximas de provedores e mantém pelo menos 300 segundos entre ciclos de polling do daemon. Defina `TOKDASH_QUOTA_BOUNDARY_POLL=0` para desabilitar, `TOKDASH_QUOTA_BOUNDARY_POST=0` para desabilitar apenas as amostras pós-reset, ou ajuste os leads de 120 segundos padrão com `TOKDASH_QUOTA_BOUNDARY_PRE_SECONDS` e `TOKDASH_QUOTA_BOUNDARY_POST_SECONDS`.

O polling ao vivo requer duas decisões separadas: `quota.credential_scan` permite acesso somente de leitura aos armazéns de credenciais locais divulgados, e então cada chave `<provider>_api` permite a requisição de rede daquele provedor. O Tokdash lê arquivos de auth/config de CLIs nativos, o `auth.json` do OpenCode mais a configuração global de provedores, os ajustes ativos do Claude e a tabela `providers` do CC Switch através de uma conexão SQLite somente de leitura. Nunca varre logs de provedores, perfis de shell ou referências arbitrarias de `{file:...}`. O MiniMax aceita um login `mmx` ou uma Token Plan Subscription Key (`MINIMAX_TOKEN_PLAN_GLOBAL_KEY` / `MINIMAX_TOKEN_PLAN_CN_KEY`); uma chave normal de pagamento por uso não tem garantia de ter cota de Token Plan. O Kimi aceita um login/chave do Kimi Code (`KIMI_API_KEY`), não uma chave de pagamento por uso da Moonshot Open Platform. A cota do SuperGrok/Grok Build requer o login OAuth da xAI em `$GROK_HOME/auth.json`; uma chave de API normal da xAI não pode acessar a faturação de consumo. No macOS, o Claude Code pode exigir uma aprovação somente de leitura da Keychain de uma vez. O Tokdash nunca renova ou escreve credenciais de provedor. `TOKDASH_QUOTA_POLL=0` é um kill switch rígido para todo o acompanhamento de cota. `tokdash export` exclui dados de cota por padrão; use `--include-quota` apenas quando você intencionalmente quiser no JSON.

O Z.ai aceita uma chave de Coding Plan de `$ZCODE_HOME/v2/config.json`, de uma configuração de ferramenta compatível, de `ZAI_API_KEY` ou de `Z_AI_API_KEY`, e consulta as janelas de créditos de 5 horas/semanais e os limites MCP legados.

O uso de tokens do Grok Build também é analisado localmente de `$GROK_HOME/logs/unified.jsonl`. Seus registros de inferência expõem tokens de prompt, prompt em cache, completion e raciocínio; o Tokdash os atribui usando os eventos de modelo do mesmo processo CLI e calcula o custo a partir do banco de preços normal. Registros sem evento de modelo são pulados em vez de receberem um preço suposto.

O uso e as sessões do DeepSeek Harness (`dsh`) são lidos localmente de `$DSH_HOME/sessions/*/*/session.jsonl.zstd` (ou o `session.jsonl` não comprimido), com `DSH_HOME` padrão em `~/.dsh`. Cada log é uma sequência de quadros zstd concatenados; o Tokdash decodifica todos os quadros, dobra o chunk inicial de uso de cada etapa em sua mensagem finalizada em vez de contá-lo duas vezes, e pula o prefixo herdado de sessões forked para que pai e filho nunca cobrem os mesmos tokens duas vezes.

O uso e as sessões do Reasonix são lidos localmente de `$REASONIX_HOME` (padrão `~/.reasonix`): tokens por requisição dos logs diários `stats/YYYY-MM-DD.jsonl`, e estrutura de sessão de `projects/*/sessions/*.jsonl`. O Reasonix conversa com os provedores que seu `config.toml` nomeia, então o par `provider/model` de cada linha é atribuído e precificado através do banco de preços normal; modelos auto-hospedados sem taxa publicada contam tokens com custo zero. O Reasonix registra o uso por requisição e nunca carimba um id de sessão, então as linhas do Session Explorer mostram turnos, projeto e momento sem contagem de tokens — Visão geral e Estatísticas carregam os totais completos.
O uso do ZCode é lido localmente de `$ZCODE_HOME/cli/db/db.sqlite` (padrão `~/.zcode/cli/db/db.sqlite`; `ZCODE_HOME` segue o próprio ajuste do ZCode). Cada linha `model_usage` é uma requisição de modelo, retries incluídos, e o `model_id` da linha é precificado através do banco de preços normal enquanto `provider_id` (ex.: `builtin:zai-start-plan`) é mantido como rótulo. O `input_tokens` do ZCode conta tokens de prompt em cache e sem cache juntos, então a parte em cache é separada no seu próprio balde e cobrada à taxa de cache, e tokens de raciocínio são exibidos disjuntos da saída mas cobrados à taxa de saída. O ZCode também aparece na aba Sessões: os turnos são lidos do mesmo banco, cobrados por (turno, modelo) com as mesmas regras, apenas sessões de nível superior, e um turno que não produziu tokens cobráveis ainda credita seu tempo medido ao tempo ativo da ferramenta. A cota Coding Plan do ZCode é dado de conta remota e está fora do escopo do parser local.

A cota do Coding Plan está disponível pelo polling ao vivo do Z.ai, com consentimento separado.

O uso do WorkBuddy é lido localmente de transcripts `~/.workbuddy-ai/projects/*/*.jsonl` (`WORKBUDDY_DATA_DIR` aceita uma lista separada por vírgulas de raízes para apontar o Tokdash para outros armazéns, ex.: um diretório de dados do Windows a partir do WSL). Cada linha de mensagem de assistente é uma chamada de modelo; a parte em cache dentro de `prompt_tokens` é separada no seu próprio balde e cobrada à taxa de cache, e tokens de raciocínio são exibidos disjuntos da saída mas cobrados à taxa de saída. O id do modelo é mantido tal qual: ids explícitos (ex.: gpt-5.5) são precificados através do banco de preços normal, enquanto o alias do roteador Auto (`default-model`) está ausente do banco de preços e custa 0.00. O valor `credit` por turno é armazenado apenas como metadados e não afeta o custo. A aba Sessões lê as mesmas linhas de transcript (uma linha de assistente faturada = um turno) a partir das mesmas raízes.

O uso do Qoder é lido localmente de dois lugares: o banco SQLite da IDE (`SharedClientCache/cache/db/local.db` sob o diretório de dados da IDE; o build QoderCN é preferido ao internacional no Windows e WSL) e os logs JSONL da CLI (`~/.qoder` e `~/.qoder-cn`, mais `QODER_CONFIG_DIR` e `QODER_CLI_HOME` separados por vírgulas). Do lado da IDE, toda linha `chat_message` conta, todos os papéis: a parte em cache é separada dos tokens de prompt no seu próprio balde e o modelo vem de `model_key` (`auto` quando o nome do roteador está ausente). Do lado da CLI, o registro de faturamento do transcript de cada requisição é mesclado com seu registro de tokens de segmento em todas as raízes: linhas com créditos de provedor mantêm o custo reportado pelo provedor como autoritativo, convertido a uma estimativa de $0.01 por crédito (`QODER_USD_PER_CREDIT` sobrescreve a estimativa) e nunca repricingado, enquanto linhas apenas com tokens são precificadas através do banco de preços normal. Um registro sem tokens de entrada os recupera de `context_usage_ratio` contra a janela de contexto conhecida — `auto` em 180.000 por padrão, todo modelo uma vez `QODER_CLI_CONTEXT_WINDOW` definida explicitamente. O Qoder IDE aparece na aba Sessões: as mesmas linhas `chat_message` (todos os papéis, uma linha analisável = um turno) são lidas de um snapshot em diretório temporário do mesmo banco de dados.

O uso do Zed é lido localmente de `threads/threads.db`, no diretório de dados do Zed de cada sistema (Linux: `$XDG_DATA_HOME/zed` ou `~/.local/share/zed`, respeitando `FLATPAK_XDG_DATA_HOME`; macOS: `~/Library/Application Support/Zed`; Windows: `%LOCALAPPDATA%\Zed`). Cada thread do agente é uma linha cujo blob comprimido com zstd (linhas antigas são JSON puro) carrega um `cumulative_token_usage` que o próprio stream de conclusão do thread acumula com marca d'água máxima por campo — é exclusivo de cache (input + cacheRead = prompt completo), então os buckets correspondem diretamente — e threads de subagente são linhas separadas que nunca são dobradas no pai, de modo que cada thread com tokens conta exatamente uma vez. Um thread é precificado pelo seu modelo atual (um que trocou de modelo, pelo último); ids auto-hospedados ausentes do banco de preços custam 0.00. O Zed não tem variável de ambiente para redirecionar o diretório de dados, então a flag `--user-data-dir` é o ponto cego documentado. O Zed não aparece na aba Sessões.

O uso do Qwen Code é lido localmente de `<base>/projects/*/chats/*.jsonl` (mais o `<base>/tmp/*/chats/*.jsonl` anterior à renomeação), onde base resolve `$QWEN_RUNTIME_DIR`, depois `$QWEN_HOME` e então `~/.qwen` — o `runtime_base_dir` do nível de configurações não é alcançável pelo Tokdash e é um ponto cego documentado. Os arquivos são somente-anexação, um por sessão, e cada registro de assistente carrega o `usageMetadata` do provedor na íntegra: `promptTokenCount` inclui o cache, então a parcela em cache é separada em seu próprio bucket e cobrada à taxa de cache, e `thoughtsTokenCount` é exibido como raciocínio. O `uuid` de cada registro é uma chave estável e global à fonte: `/branch` copia os registros do pai (mesmos uuids) para o arquivo do fork, então o armazenamento de uso atribui cada chave pela ocorrência mais antiga e promove uma cópia sobrevivente quando o arquivo canônico é apagado. Registros de subagente compartilham o arquivo de sessão e contam automaticamente. O custo vem do banco de preços; registros sem modelo contam tokens como `unknown` a 0.00. O Qwen Code não aparece na aba Sessões.

O uso do Crush é lido localmente de `$CRUSH_DATA_DIR` (uma lista separada por vírgulas de diretórios de dados, cada um contendo `crush.db`) — obrigatório, porque o diretório de dados padrão do Crush é um `.crush` por projeto ao lado do diretório de trabalho e não há raiz global a varrer. O banco usa WAL, então o Tokdash o lê pelo mesmo caminho de cópia e snapshot do ZCode. Cada sessão com tokens diferentes de zero contribui com uma entrada, incluindo sessões de subagente: o Crush dobra apenas o custo na sessão pai, nunca os tokens, então o critério de somente nível superior das suas próprias consultas de estatísticas (`parent_session_id IS NULL`) descartaria esse uso. Cada entrada é atribuída à última mensagem de assistente não-resumo da sua sessão — uma sessão com vários modelos é precificada pelo último. Três ressalvas: os contadores são atribuídos por passo em vez de acumulados, então guardam apenas o tamanho de contexto da última requisição e a saída do último turno, ficando abaixo do real em sessões de vários passos (verificado com o Crush v0.91.2; nada em `crush.db` permite recuperar os totais reais); os tokens podem ser estimativas por contagem de caracteres quando o provedor reporta uso zero, sem qualquer sinalização no banco; e a separação de cache/raciocínio não é persistida. Os timestamps são em segundos; as linhas são agrupadas por `updated_at` (último toque), então o total de toda a vida de uma sessão cai em um único dia. `sessions.cost` é ignorado; o custo vem apenas do banco de preços. O Crush não aparece na aba Sessões.

O `tokdash setup` oferece uma etapa opcional de cota (consentimento de rede por provedor, padrão Não, mais o intervalo de polling), e o `tokdash doctor` reporta o estado da cota: interruptor geral, consentimento por provedor, kill switch, intervalo efetivo e sua fonte, último horário de polling e a contagem de snapshots armazenados.

Os snapshots de cota e seu histórico vivem no banco de uso local (`usage.sqlite3`, ligado por padrão) e são **mantidos indefinidamente por padrão** — defina `TOKDASH_QUOTA_RETENTION_DAYS` para um número positivo de dias para aparar snapshots mais antigos. Se você sair da persistência local com `TOKDASH_USAGE_DB=0`, a aba Quota perde seu principal caminho de dados: nenhum histórico de snapshot é mantido, o poler em segundo plano não roda, e a aba só mostra resultados em memória de um **Refresh** manual (provedores de rede com consentimento) pela vida do processo atual do servidor. Mantenha o banco de uso ligado (o padrão) para acompanhamento de cota normal.

## API (local)

O Tokdash é um servidor HTTP local. Endpoints comuns:

- `GET /api/usage?period=today|week|month|N`
- `GET /api/usage?date_from=YYYY-MM-DD&date_to=YYYY-MM-DD`
- `GET /api/tools?period=...` (apenas ferramentas de codificação)
- `GET /api/openclaw?period=...` (apenas OpenClaw)
- `GET /api/sessions?tool=codex|claude|opencode|pi_agent|omp|mimo|kimi|dsh|reasonix|zcode|kilocode|grok|hermes|antigravity_cli|cline&period=...` (acrescente `&include_review_sessions=true` para incluir sessões de revisão/permissoes do Codex, ocultas por padrão)
- `GET /api/active-time?period=...` (tempo ativo em toda ferramenta de sessão, mais detalhamento por ferramenta)
- `GET /api/quota` e `GET /api/quota/history` (snapshots de cota de assinatura; o refresh de rede é gateado por gravação e opt-in)
- `GET /api/stats` (calendário de contribuições e estatísticas)

Exemplo:
```bash
curl 'http://127.0.0.1:55423/api/usage?period=today'
```

Referência completa da API: [`docs/reference/API.md`](docs/reference/API.md) — schema, parâmetros e formas de resposta de cada endpoint.

## Nota sobre a precisão do custo

As contagens de tokens dependem do que cada cliente registra localmente. Os custos são calculados por padrão do banco de preços incluído (`src/tokdash/pricing_db.json`) ou da sua sobrescritura de preços do painel salva em `<data_dir>/pricing_db.json` quando presente (a aba Pricing escreve lá e substitui por completo as taxas incluídas). Em qualquer caso podem ficar atrás do preço real do provedor — use como estimativa e verifique contra sua fonte de faturação se importar.

## Retenção do histórico

> [!IMPORTANT]
> **Mantenha seu histórico.** O Claude Code e o Gemini CLI excluem por padrão sessões locais com mais de ~30 dias, então os meses anteriores do Tokdash podem encolher em silêncio.

O Tokdash lê os logs de sessão **locais** de cada cliente e também mantém um índice de desempenho SQLite local. O índice pode manter linhas que o Tokdash já viu, mas não pode recuperar logs excluídos antes de serem indexados, e não substitui manter o histórico original do cliente. Se um cliente exclui logs antigos antes do Tokdash sincronizá-los, um mês passado ainda pode ser lido **mais baixo do que quando você o registrou pela primeira vez**. Apenas dois clientes suportados fazem isso por padrão, e ambos são uma correção de uma linha:

- **Claude Code** exclui sessões mais antigas que `cleanupPeriodDays` (**padrão 30 dias**) na inicialização. Adicione isto ao seu `~/.claude/settings.json` existente (e a qualquer `CLAUDE_CONFIG_DIR` alternativo):
  ```json
  { "cleanupPeriodDays": 3650 }
  ```
- **Gemini CLI** exclui sessões com mais de 30 dias. Desative no `~/.gemini/settings.json`; se um projeto tem `.gemini/settings.json`, faça a mesma mudança lá porque a configuração de workspace sobrepõe a de usuário:
  ```json
  { "general": { "sessionRetention": { "enabled": false } } }
  ```

Todos os outros clientes suportados mantêm o histórico indefinidamente por padrão. Para a pesquisa completa por cliente, detalhes da correção e o que o índice SQLite local preserva e não preserva, veja **[docs/reference/HISTORY_RETENTION.md](docs/reference/HISTORY_RETENTION.md)**.
